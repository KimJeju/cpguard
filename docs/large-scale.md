# 대규모 코드베이스·대량 탐지 최적화 설계 노트

20~30GB 소스, 또는 탐지 5만 건 이상 같은 극단 규모를 CPGuard 로 다루기 위한
전략. 크게 **(A) 스캔(분석) 확장성** 과 **(B) 대량 탐지 처리·UX** 로 나뉜다.

---

## A. 스캔 확장성 (20~30GB 소스)

병목은 파싱 → CPG 구성 → taint 고정점 계산의 메모리·시간이다. 순서는 ROI 순.

### A1. 싱크 사전 필터링 (최우선 · 저비용)
taint 를 돌리기 전에, 각 규칙의 **싱크 시그니처를 텍스트 grep** 으로 먼저 훑어
해당 싱크가 없는 파일은 그 규칙의 흐름 분석에서 제외한다. 대부분의 파일에는
특정 sink(예: `child_process.exec`)가 없으므로 흐름 계산 대상이 급감한다.
- `scanner.py` 성능 메모에 이미 "규칙별 소스/싱크 사전 필터링이 다음 최적화 지점"으로 명시됨.
- 규칙당 싱크 리터럴 집합을 Aho-Corasick 로 한 번에 매칭 → 파일→적용규칙 맵 구성.

### A2. 요약 캐시 + 증분 분석
함수 요약(summary)을 **파일 내용 해시로 캐시**하고 스캔 간 재사용한다.
변경 없는 파일은 재파싱·재분석하지 않는다(`git diff` 또는 mtime/hash 기준).
- 20GB 중 실제로 바뀌는 건 소수 → 재스캔 비용이 선형에서 델타로 떨어진다.
- 캐시 키: `(파일 해시, 규칙 버전)`. 저장은 `~/.cpguard/cache/`(SQLite/RocksDB).

### A3. 프로세스 병렬화
파싱·프로시저 내부 분석은 파일 단위로 독립 → **멀티프로세스 워커 풀**.
프로시저 간(요약 고정점)은 콜그래프 **SCC/패키지 단위로 샤딩**해 병렬.
- 현재 엔진은 단일 프로세스. `concurrent.futures.ProcessPoolExecutor` + IR 직렬화.
- jadx 처럼 `--threads-count` 옵션 노출.

### A4. 스트리밍·상한 (메모리 보호)
- 파일을 한 번에 로드하지 않고 모듈 단위로 처리 후 즉시 해제(이미 부분 적용).
- 벤더·생성·미니파이·`node_modules` 제외(이미 적용). SQL 덤프 등 텍스트 상한(이미 적용).
- 함수·파일별 **시간 예산**: 초과 시 프로시저 내부 분석으로 강등하고 `ScanReport`
  에 부분분석으로 기록(무결성 보고는 이미 존재).

### A5. 진입점 기반 프루닝 (도달성)
웹 핸들러·컨트롤러 등 **엔트리포인트에서 도달 가능한 코드만** 흐름 분석하고,
라이브러리·죽은 코드는 패턴 축만 돌린다. 실제 공격면에 집중 + 계산량 감소.

### A6. CPG 온디스크
RAM 에 다 못 올리는 규모는 CPG 를 임베디드 그래프 스토어(SQLite/RocksDB)에
두고 **지연 질의**한다(상용 SAST·Joern 계열 접근). taint 는 필요한 서브그래프만 로드.

**요약 우선순위:** A1(싱크 필터) → A2(캐시/증분) → A3(병렬) → A4(상한) → A5/A6.

---

## B. 대량 탐지 처리 (5만 건 이상)

현재 `Scan.findings_json` 이 **단일 TextField** 라 5만 건이면 로드·직렬화·브라우저
전달이 모두 무너진다. 저장·API·UI·트리아지를 전부 페이지네이션 지향으로 바꾼다.

### B1. Finding 을 DB 테이블로 (최우선)
`findings_json` 대신 **인덱스된 Finding 테이블**(scan FK, severity, rule_id, cwe,
file, fp, verdict). 서버측 필터·정렬·집계·카운트를 DB 가 처리 → 5만 건도 O(page).
- 작업대는 전체를 `json_script` 로 뿌리는 대신 **페이지 API** 로 받는다.

### B2. 집계 우선 UX + 가상 스크롤
기본 화면을 **규칙/파일/CWE 그룹 + 카운트**로 보여주고 드릴다운. 5만 행을 한 번에
렌더하지 않고, 목록은 **가상 스크롤**(보이는 만큼만 DOM).

### B3. 중복·클러스터링
같은 규칙·같은 sink 지문을 **묶어** 대표 1건 + N건으로 표시. 5만 건의 상당수는
동일 패턴 반복 → 사람이 볼 실제 건수가 급감.

### B4. 우선순위·랭킹
심각도 × 도달성 × 신규(직전 스캔 대비) × EPSS/KEV 로 정렬해 **상위 N** 을 먼저.
사람과 LLM 의 주의를 고가치에 집중.

### B5. LLM 트리아지 샘플링·캐시
5만 건 전부 트리아지 = 비용 폭발. **클러스터 대표만**, 또는 critical/high·신규만
트리아지하고 **지문 기준 캐시**로 재사용. (배치·캐시는 이미 부분 존재.)

### B6. 스트리밍 산출물
SARIF/CSV/xlsx/PDF 를 메모리에 다 안 올리고 **스트리밍** 생성. PDF 진단 보고서는
5만 건을 나열하지 말고 **집계 + 상위 N + 유형별 요약**으로(현재 상세 나열은 상한 필요).

### B7. 점진적 결과
진행 화면이 이미 카운트를 스트리밍하므로, **스캔 완료 전에도** 확정된 부분부터
트리아지 시작 가능하게 한다.

**요약 우선순위:** B1(DB 테이블) → B2(집계/가상스크롤) → B3(클러스터) → B4(랭킹)
→ B5(트리아지 샘플링) → B6/B7.

---

## CPGuard 에 바로 적용할 Top 6 (규모 대응 로드맵)

1. **싱크 사전 필터링** (A1) — 스캔 시간 최대 절감, 엔진 소폭 수정.
2. **Finding DB 테이블화** (B1) — 5만 건 페이지네이션·필터의 전제.
3. **작업대 서버측 페이지/집계 API + 가상 스크롤** (B2).
4. **요약 캐시·증분 스캔** (A2) — 재스캔을 델타로.
5. **멀티프로세스 파싱/분석** (A3) — `--threads-count`.
6. **트리아지 클러스터+캡+캐시** (B3/B5) — LLM 비용 통제.

이 6개면 20~30GB·5만 건 규모에서 "메모리 폭발·무한 대기·브라우저 멈춤" 3대
실패를 제거하고, 사람이 실제로 검토 가능한 우선순위 목록으로 좁힐 수 있다.
