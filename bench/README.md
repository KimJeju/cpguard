# OWASP Benchmark (Java · Python)

[OWASP Benchmark](https://owasp.org/www-project-benchmark/) 는 테스트케이스마다 "이 파일에
해당 취약점이 실제로 존재하는가"를 라벨링한 정답지를 제공한다. 같은 취약 유형에 대해
취약한 구현과 안전한 구현이 짝으로 들어 있어, 재현율뿐 아니라 **오탐률까지 규모 있게**
측정된다. 파이썬판은 커뮤니티 포팅본이다.

## 측정 범위

데이터 흐름(taint) 분석의 대상이 되는 유형만 지표에 넣는다. `weakrand`·`crypto`·`hash`·
`securecookie` 는 "위험한 API 를 썼는가"를 보는 설정 점검 항목이고 `trustbound` 는 세션
속성의 신뢰 경계 문제라 taint 규칙의 대상이 아니다. 대상 밖 유형을 섞어 집계하면 수치가
왜곡되므로 **제외하고 그 사실을 함께 표기**한다(Java 1,168건 · Python 884건).

# BenchProctor (6언어)

[BenchProctor](https://github.com/TheAuditorTool/BenchProctor) 는 11개 언어·21개 프레임워크에
대해 취약/안전을 50:50 으로 짝지은 합성 코퍼스다(Apache-2.0). CPGuard 는 **js·ts·go·ruby·
c·cpp** 의 quicktest 티어 11개 스위트(60,600 케이스)를 쓴다. 구조가 OWASP Benchmark 와
같아(`expectedresults CSV` + `testcode/`) 같은 하네스로 잰다.

**프레임워크별로 따로 잰다.** 같은 언어라도 요청 객체의 모양이 달라 점수가 크게 갈리는데,
그 차이 자체가 정보이기 때문이다(아래 참조).

## 이 코퍼스가 드러낸 것

붙이자마자 **12개 스위트 중 4개가 0.000** 이었다. 원인은 전부 엔진이 아니라 **규칙 데이터가
프레임워크 하나만 알고 있던 것**이었다.

| 스위트 | 코퍼스가 쓰는 형태 | 우리가 알던 형태 | 이후 |
|---|---|---|---:|
| koa | `ctx.request.headers[...]` | `req.*` 만 | 0.002 → 0.362 |
| sinatra | 라우트 전체가 `post "/x" do ... end` 블록 안 | 메서드만 | 0.000 → 0.342 |
| httplib | `req.get_param_value("id")` | 이름 소스(argv·getenv)만 | 0.000 → 0.105 |
| nestjs | `throw new BadRequestException()` 로 거부 | `return` 만 | 0.138 → 0.380 |
| gin · net_http | `go func(){ … }()` 클로저가 바깥 변수를 붙잡는다 | 빈 환경으로 실행 | 0.044 → 0.152 |

nestjs 줄이 특히 분명한 신호였다. **express_ts 와 nestjs 는 같은 언어·같은 규칙**인데
처음엔 0.376 대 0.138 로 2.7배 갈렸다. 안전 변형의 거부 방식이 `return` 이냐 `throw` 냐의
차이 하나였고, 조건 가드 판정(`_always_exits`)이 `return` 만 보고 있었다.

Go 줄은 더 넓게 번졌다. 중첩 함수를 **빈 환경으로** 실행하고 있어서 클로저가 붙잡은
변수가 전부 깨끗해 보였는데, 이건 Go 만의 문제가 아니었다 — 고치자 JS·TS·Ruby 여섯
스위트가 같이 올랐다(express 0.375 → 0.445, koa 0.362 → 0.402, rails 0.373 → 0.388).
**한 코퍼스에서 찾은 결함이 다른 코퍼스의 점수를 올리는 것이, 그 수정이 코퍼스에
맞춘 것이 아니라는 가장 좋은 증거다.**

C 계열은 **참조 출력 인자**가 핵심이었다.

```c
char buf[256];
fread(buf, 1, n, stdin);                    // outparam: 이 호출 자체가 입력이다
snprintf(cmd, sizeof(cmd), "ls %s", buf);   // outcopy: 오염을 cmd 로 옮긴다
system(cmd);
```

C 계열 입력 API 가 전부 이 모양이라 리턴값만 보는 모델로는 통째로 미탐이었다(C 재현율
10.8% → 66.4%). 어떤 호출의 몇 번째 인자가 출력인지는 규칙이 선언한다.

**Go 도 같은 계열이었다.** `json.NewDecoder(c.Request.Body).Decode(&q)` 는 오염이
수신자에 있고 결과는 `&q` 로 나간다. `c.ShouldBindJSON(&q)` 는 호출 자체가 입력이다.
같은 장치를 확장해 수신자도 보게 하고, `&q` 처럼 주소를 넘기는 형태를 한 겹 벗겼다.

## 파생값 가드 — 측정으로 정한 설계 판단

Go 오탐 148건을 분해하니 **87건(59%)이 한 모양**이었다. 실무에서 SSRF 를 막는 방법은
URL 문자열 자체를 검사하는 게 아니다.

```go
parsedURL, _ := url.Parse(data)                      // data 가 오염
if !allowed[parsedURL.Hostname()] { 거부; return }   // 검사는 투영에
http.Get(data)                                        // 사용은 원본으로
```

엔진은 조건이 검사한 경로(`parsedURL.Hostname`)만 씻었고, 정작 싱크에 닿는 `data` 는
그대로 남아 오탐이 됐다. 검증된 값의 **조상**까지 씻으려면 유래를 알아야 하는데,
별도 자료구조는 필요 없었다 — `data` 의 트레이스는 `host` 트레이스의 접두사다.
형제(`other := data + "x"`)는 갈라진 지점이 달라 그렇지 않다.

**이 판단은 일반적으로 건전하지 않다.** 호스트를 검사해도 경로·질의는 그대로다.
그래서 코드에 미리 답을 박지 않고 플래그 뒤에 구현해 **15개 스위트를 전부 재고** 정했다.

| | 이전 | 이후 | |
|---|---:|---:|---|
| Go gin | 0.152 | **0.322** | 오탐 148 → 61 |
| Go net_http | 0.164 | **0.316** | 오탐 133 → 55 |
| Ruby rails | 0.388 | **0.430** | 재현율 손실 0 |
| Ruby sinatra | 0.355 | **0.398** | 재현율 손실 0 |
| JS express · koa | 0.445 · 0.402 | 0.442 · 0.396 | 스위트당 취약 2건 미탐 |
| TS express_ts · nestjs | 0.431 · 0.380 | 0.427 · 0.376 | 스위트당 취약 2건 미탐 |
| Java · Python · PHP · C# · C · C++ | | 변화 없음 | |

JS·TS 가 잃은 8건은 전부 같은 형태다 — 허용 목록이 `.trustmesh.internal` 같은 **내부
도메인을 허용한다**. 가드는 진짜로 존재하고, 목록의 내용이 취약점이다. 흐름 분석으로는
구분할 수 없는 종류라 비용으로 받아들였다. 그 상한선은
[`tests/test_derived_guard.py`](../tests/test_derived_guard.py) 의 '취약' 항목들이 지킨다
— 길이 검사(`len(data) > 100`)나 무관한 값 검사는 검증으로 치지 않는다.

같이 드러난 것: `url.Parse` 가 SSRF **싱크**로 등록돼 있었다. URL 을 파싱하는 것만으로는
아무 요청도 나가지 않는다. 빼자 재현율 손실 없이 gin 0.152 → 0.178 이었다(위 표의
'이전'은 이 수정 전 값이다).

## 이 코퍼스의 한계

- **신생 프로젝트다.** 별 9개, 생성기는 비공개다. OWASP Benchmark·NIST SARD 와 같은
  권위로 나란히 보면 안 된다. 라벨 자체는 잘 만들어져 있다(취약/안전 50:50, 62개 유형).
- **62개 유형 중 우리가 지표에 넣는 것은 11~15개**다. 나머지는 설정 점검이거나(weakhash·
  securecookie·csrf 등) **우리에게 규칙이 없는 유형**(nosql·ssti·el_injection·
  prototypepollution·XXE·CRLF 주입 등 13종)이다. 하네스는 이 둘을 **나눠서 보고한다** —
  뒤엣것을 설정 점검과 함께 조용히 빼면 커버리지를 부풀리게 된다.

# C# Vulnerability Test Suite (SARD)

[NIST SARD 테스트 스위트 #105](https://samate.nist.gov/SARD/test-suites/105) — 32,003 케이스.
위 PHP 스위트와 같은 생성기이고, 케이스 디렉터리마다 `manifest.sarif` 가 good/bad 와 CWE 를
선언한다.

> 내려받는 곳은 `https://samate.nist.gov/SARD/downloads/test-suites/2016-09-12-csharp-vulnerability-test-suite.zip`

## 읽는 법 — 쏘면 맞는데 잘 안 쏜다

정밀도 87.8% · 오탐률 5.8% 는 이 문서에서 가장 좋은 숫자다. 반면 재현율은 30% 다.
원인이 코퍼스 구조에 그대로 드러난다: **소스가 4종**(`args` 8,261 · 프로세스 표준출력
8,258 · `Console.ReadLine` 8,258 · 하드코딩 8,258)인데 우리는 한동안 `Console.ReadLine`
하나만 알았다. 그래서 CWE_22/78/90/91 재현율이 **정확히 1/3 언저리에 수렴**했다.
`args` 와 프로세스 출력을 소스로 넣어 0.121 → 0.242 가 됐고, 남은 몫은 SQL 주입 유형의
sink·구성 변형이다.

# DVWA (PHP, 실제 앱 · 보조 지표)

[DVWA](https://github.com/digininja/DVWA) 는 취약점 모듈마다 보안 수준별 소스를 제공한다.

- `vulnerabilities/<모듈>/source/low.php` — 의도적으로 **취약**(탐지해야 정답)
- `vulnerabilities/<모듈>/source/impossible.php` — 제대로 **방어**(탐지하면 오탐)

**정직성을 위한 두 가지 규칙:**
1. **측정 대상 = 해당 조각 안에 그 취약 유형의 sink 가 있는 모듈만.** DVWA `source/*.php` 는
   발췌 조각이라 출력(`echo`)·`include` 가 부모 페이지에 있는 경우가 많다. 조각 안에 sink 가
   없으면 *어떤* per-file 데이터흐름 분석기도 원리상 탐지할 수 없으므로 제외한다.
2. **판정은 그 모듈이 목표하는 규칙(taint)만으로.** 다른 축(패턴·hygiene) 규칙이
   `impossible.php` 에서 발화하는 건 taint 엔진의 오탐이 아니므로 제외한다.

| 지표 | 값 |
|---|---|
| 측정 대상 모듈 | 4 (exec · open_redirect · sqli · sqli_blind) |
| 재현율 | 100% (4/4) |
| 정밀도 | 80% |
| F1 | 0.889 |

**표본이 작다(N=4).** 방향성 참고용이며, 규모 있는 지표는 위의 합성 코퍼스를 본다.

```bash
python bench/dvwa_eval.py /path/to/DVWA --json bench/dvwa_result.json
```

# 정답지가 없는 언어

**코틀린·스위프트는 라벨링된 SAST 코퍼스가 존재하지 않는다.** NIST SARD 에도,
BenchProctor 에도, 논문 벤치마크에도 없다.

대신 **그 언어 코드에서 흔한 형태를 최소 재현으로 직접 묻는다.** 정답지가 아니라 우리가
고른 형태라 편향이 있지만, 없는 것보다 훨씬 낫고 벤치마크 점수와는 **다른 것을 잡아낸다** —
아래 테스트가 잡아낸 결함 중 벤치마크 점수를 움직인 것은 하나도 없었다.

| 파일 | 항목 |
|---|---|
| `tests/test_conformance.py` | 4언어(js·php·py·java) × 공통 12항목 = 40건 |
| `tests/test_js_idioms.py` | JS/Node 관용구 30건 |
| `tests/test_ts_idioms.py` | TypeScript·NestJS 관용구 30건 |
| `tests/test_kotlin_swift_idioms.py` | Kotlin 16 + Swift 14 |

실제로 이 테스트들이 잡아낸 것:

- **TS 파라미터가 `required_parameter{pattern,type}` 로 감싸여 와서** 이름이 `v: string` 이
  되고 있었다. 인자 전파가 영영 안 걸려 **타입을 쓴 함수 전체가 프로시저간 분석에서
  빠져 있었다** — TS 에서 타입을 안 쓰는 함수는 없다.
- 코틀린은 `"ls $p"` 와 `"ls ${p}"` 의 결과가 갈리고 있었다. 같은 코드다.
- 생성자 → 필드 → 메서드 흐름(`new Svc(오염).run()`)이 **네 언어 전부에서 미탐**이었는데,
  정답지가 있는 두 언어가 마침 그 형태를 안 써서 여태 드러나지 않았다.

# 전체 한계 (정직하게)

- **대부분 합성 벤치마크다.** 테스트케이스가 기계 생성이라 패턴이 반복되고 실제 코드베이스의
  분포와 다르다. 특정 도구가 과적합될 수 있다는 비판은 타당하다. 여기서 한 수정은 모두
  **일반적인 분석 기법**(상수 전파·컨테이너 전파·참조 출력 인자·조건 가드)이지 테스트케이스
  이름이나 형태에 맞춘 것이 아니다. 벤치마크 헬퍼 이름을 정제 목록에 넣는 식의 조작은 하지
  않는다.
- **패턴 축 59개 규칙은 정답지가 아예 없다.** 실제 스캔 탐지의 다수가 이쪽이다.
- **프레임워크·DI·ORM 이 없다.** 우리 해석은 이름 기반이라 타입 추론·동적 디스패치·import
  별칭을 풀지 못한다.
- **측정 비용.** 자바 코퍼스(2,740 파일) 전체 스캔이 프로젝트 모드로 20분, PHP(42,212 파일)가
  15분이다. 요약 고정점 반복이 병목이고 프로파일링이 필요하다. BenchProctor 는 파일 모드로
  스위트당 35초라, 반복 작업은 이쪽으로 돌리고 자바·PHP 는 커밋 직전에만 돈다.
