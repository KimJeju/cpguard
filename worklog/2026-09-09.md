## 1. 검수 결함 4건 (`1cb050f`)

전날 만든 확인·알림 창을 스스로 검수해 네 가지를 찾았다. 셋은 브라우저에서 재현했다.

1. **파괴적인 확인 창에서 Enter 가 '취소' 포커스를 무시했다.** 캡처 단계에서 Enter 를
   가로채 `preventDefault` 하고 무조건 '확인'으로 해결했다. 포커스된 버튼이 활성화될
   기회가 없으니 "취소에 포커스를 둬 오입력을 막는다"는 장치가 아무 역할도 못 했다 —
   스캔 삭제 창에서 Enter 한 번이면 지워졌다. Enter 는 브라우저가 포커스된 버튼을 누르게
   두고 Esc 만 다룬다.
2. **창이 떠 있는데 다시 열면 앞의 Promise 가 영영 풀리지 않았다.** `resolver` 를 그냥
   덮어써서 앞 호출의 `.then` 이 실행되지 않았다. 앞의 것을 '아니오'로 닫고 연다.
3. **표 보기의 빈 체크박스 열 헤더를 누르면 정렬이 깨졌다.** 정렬 핸들러를 모든 `th` 에
   걸어 `data-col` 이 없는 헤더가 `ws.sort` 를 `undefined` 로 만들었고, 그 값이
   localStorage 에 남아 새로고침해도 죽어 있었다.
4. **일괄 의견이 기존 개별 의견을 말없이 덮어썼다.** 메모는 이력이 없어 복구할 수 없다.
   기본은 건드리지 않고, 덮어쓰려면 호출부가 `overwrite` 를 명시해야 한다. 확인 창이
   대상 중 이미 의견이 적힌 건수를 보여주고 체크박스를 띄운다(기본 꺼짐).

## 4. 파이썬 미탐 — for 와 with (`86e78f1`)

미탐 69건을 분류해 둘을 고쳤다. 둘 다 파이썬에서 아주 흔한 형태다.

1. **`for` 반복 변수가 순회 대상의 오염을 이어받지 못했다**(13건).
   `for name in request.form.keys(): open(name)` 이 통째로 미탐이었다. 반복 변수가
   어디서도 묶이지 않았다. 자바 정규화기에는 이미 있던 처리라 파이썬만 빠져 있었다.
2. **`with` 문의 컨텍스트 식이 사라졌다**(14건). `with open(사용자경로) as fd:` 에서
   `open(...)` 호출 자체가 IR 에서 없어져 sink 검사를 아예 못 했다. try 와 같은 묶음으로
   본문만 펼치고 있었기 때문이다.

결과: 재현율 48.5% → 67.9%, 점수 0.178 → 0.292.

## 5. 파이썬에 상수 전파가 걸리지 않고 있었다 (`8de266b`)

`constfold` 는 "컴파일 시점에 결과가 정해지는 분기를 접는다"고 적혀 있고 자바에서는
실제로 동작한다. 그런데 파이썬 정규화기가 연산자와 조건식을 Opaque 로 접어 버려 접을
근거가 IR 에 남지 않았다. taint 전파는 같지만 실행되지 않는 가지가 그대로 오염으로 남는다.

`binary_operator`·`boolean_operator`·`comparison_operator` → `ir.Binary`,
`unary_operator`·`not_operator` → `ir.Unary`, `conditional_expression` → `ir.Ternary`.
파이썬은 `참값 if 조건 else 거짓값` 순서라 constfold 가 기대하는 `[조건, 참, 거짓]`으로
바꿔 넣는다. `a < b < c` 처럼 연산자가 여럿인 비교는 접지 않는다.

보수적인 기존 기준은 실측으로 확인했다 — 조건이 거짓으로 접히면 취약 가지가 남고,
조건이 변수면 접지 않으며, 한 스코프에서 두 번 대입된 이름도 접지 않는다.

결과: 정밀도 52.6% → 57.6%, 오탐 82 → 67, 점수 0.292 → 0.363.

## 6. 유일 이름 해석 · self 자리 · self.request (`8cbaca4`)

파이썬 미탐을 다시 분류하니 **request 래퍼 객체 경유 21건**이 최대였다.

```python
wrapped = helpers.separate_request.request_wrapper(request)
param = wrapped.get_form_parameter("BenchmarkTest00272")
```

세 가지가 겹쳐 있었다.

1. **수신자가 변수라 정의를 못 찾는다.** 전날 이 범위를 넓혔다가 취약 13건을 미탐으로
   만든 전례가 있어 조심스럽다. 그래서 **이름의 정의가 프로젝트 전체에 하나뿐일 때만**
   해석한다. 실측: `get_form_parameter` 1개, `getTheParameter` 1개, 반면
   **`doSomething` 은 자바 코퍼스에 1802개** — 모호하면 자동으로 걸러진다.
   여기에 수신자가 단순 변수일 것과 인자 수가 맞을 것을 추가 조건으로 걸었다.
2. **파이썬 메서드 요약의 파라미터 자리가 한 칸씩 밀려 있었다.** `obj.m(a)` 는 인자가
   `[a]` 뿐인데 요약은 `self` 를 파라미터 0 으로 센다. 프로시저간 판정이 통째로 어긋난다.
   요약에 `implicit_self` 를 담고 수신자 호출이면 자리를 맞춘다.
3. **`self.request.form` 이 소스로 안 잡혔다.** 요청 객체를 인스턴스에 담아 두는 것은
   Django 클래스 뷰·자바 컨트롤러에서 표준에 가깝다. `self`/`this`/`cls` 한 겹만 벗기고
   매칭한다. 기존 이름 기반 매칭과 같은 방식이고, 같은 클래스의 `get_safe_value` 는
   여전히 소스가 아닌 것으로 확인했다.

파이썬 결과: 재현율 67.9% → 82.1%, 점수 0.363 → 0.420, 미탐 43 → 24.

자바에서 xss 재현율이 86.2% → 77.6% 로 떨어졌다. 이름만 유일하다고 이어 붙이면
수신자가 라이브러리 객체인 호출까지 엉뚱한 요약을 씌운다. 1번에 조건 두 개를 더 걸었다
— 수신자가 단순 변수일 것, 인자 수가 맞을 것(수신자 호출이면 self 한 자리 제외).
그러자 xss 재현율이 88.2% 로 회복됐고 오탐은 29건 그대로였다. 원래(86.2%)보다도 높다.

자바 결과: 재현율 87.2% → 93.4%, 정밀도 80.2% → 80.8%, 점수 0.649 → 0.692.
파이썬은 안전장치 전후가 같다(82.1%, 0.420) — 래퍼 해석이 그대로 산다.

## 7. 파이썬 오탐 85건 분해 → 바인딩 파라미터 질의 (`미커밋`)

오탐을 흐름 트레이스로 분류했다.

| 건수 | 원인 | 성격 |
|---|---|---|
| ~24 | 조기 반환 가드 `if '../' in bar: return` 후 사용 | 실제 코드에 흔함 |
| 19 | 컨테이너 왕복 | 함정 |
| 19 | `match/case` 상수 선택 | 함정(문자열 인덱싱 필요) |
| **9** | **바인딩 파라미터 질의** | **진짜 결함** |
| 2 | 슬라이스/split | 함정 |

9건이 `sqli` 오탐 전부였다.

```python
cur.execute(sql, (bar,))     # sql 은 플레이스홀더, bar 는 바인딩 → SQLi 정석 방어
```

인자를 전부 검사하니 **방어를 제대로 한 코드가 오탐**이 됐다. `SinkPattern.arg` 가
정확히 이걸 위한 필드인데 쓰지 않고 있었다. `arg: 0` 으로 질의문만 본다 — 문자열
연결로 만든 진짜 취약점은 첫 인자에서 그대로 잡힌다. `extra()` 는 `select=`·`where=`
키워드로 받아 자리를 특정할 수 없어 제외했다.

자바에도 같은 구조가 있어 함께 적용했다(`executeUpdate(sql, new int[]{1,2})`,
`queryForObject(sql, Integer.class, bar)`). **자바 수치는 변하지 않았다** — 이 코퍼스의
안전 변형이 뒤 인자로 오염값을 넘기지 않기 때문이다. 실제 코드에서는 유효한 수정이다.

파이썬 결과: 오탐 85 → 76, 정밀도 56.4% → 59.1%, 점수 0.420 → 0.462.

남은 최대 덩어리는 **조기 반환 가드 ~24건**이다. `if 검증실패: return` 은 실제 코드에
아주 흔하고 함정이 아니다. 다만 "어떤 검사가 충분한가"는 규칙이 선언해야 하는 문제라
(지금 `sanitizers` 는 호출만 인식한다) 설계 판단이 필요해 남겨 뒀다.

## 8. SCA 오프라인 조회 (`미커밋`)

국내 기반시설 진단은 망분리가 흔한데, SCA 는 OSV.dev 조회가 필요했다. 세 가지를 고쳤다.

1. **"취약점 없음"과 "조회 못 함"을 구분한다.** 예전에는 둘 다 빈 결과였고 문구로만
   단서를 달았다. 망분리 환경에서 돌리면 산출물에 "알려진 취약점 없음"으로 적히는데,
   그건 확인하지 않은 값이다. `query_osv` 가 실패 시 `{}` 대신 `None` 을 돌려주게 해
   호출부가 "미수행"으로 보고한다.
2. **로컬 스냅샷 조회** — `--sca-db DIR` 또는 `CPGUARD_OSV_DIR`. `<dir>/PyPI.zip`(받은
   zip 그대로)과 `<dir>/PyPI/*.json`(풀어 둔 것)을 모두 읽는다. zip 은 스트리밍으로 읽어
   메모리를 묶는다. 스냅샷이 있으면 네트워크보다 먼저 쓴다 — 의존성 목록이 밖으로
   나가지 않는다.
3. **`cpguard osv-sync`** — 인터넷 되는 곳에서 미리 받는 명령. 이 명령만 네트워크를 쓴다.

버전 판정은 ① `versions[]` 명시 목록 ② 없으면 범위(`introduced`/`fixed`/`last_affected`)
③ GIT 범위나 파싱 불가면 **판정 보류**로 세어 요약에 건수를 적는다. 정식 semver 파서는
두지 않았다 — 생태계마다 규칙이 다르고, 애매하면 보류가 산출물에 잘못 쓰는 것보다 낫다.

회귀 테스트 4개를 더했다. 그 중 하나는 "조회 차단을 취약점 없음으로 쓰면 안 된다"를
직접 검증한다.

## 9. 조기 반환 가드 — 규칙이 "무엇이 검증인가"를 선언한다

파이썬 오탐의 최대 덩어리였다. 형태는 둘뿐이었다.

    if '../' in bar:                      15건 — 경로 조작 거부
        return 오류
    if not bar.startswith("'") or ...:    16건 — 따옴표 형식 검증
        return 오류

정제 *함수*를 부르지 않고 값의 형태만 확인해 거부하는 코드라 기존 sanitizers(호출
이름 목록)로는 잡히지 않았다. 무엇을 검증으로 인정할지는 유형마다 다르므로 규칙이
선언하게 했다(`validators:`). 경로 조작은 `'..'` 포함 검사, 코드 주입은
`startswith`/`endswith` 형식 검사다.

두 조건이 모두 맞을 때만 적용한다.
  1. 참 분기가 반드시 돌아간다(return).
  2. 조건에 규칙이 선언한 검증 표시가 있고, 그 조건이 오염 경로를 언급한다.

그래서 `if not b: return` 처럼 무관한 가드나 다른 변수를 검사하는 가드는 여전히
탐지한다(최소 재현 6건으로 확인).

부수 효과로 **참 분기가 return 하면 그 분기의 상태를 이어붙이지 않게** 됐다. 이쪽은
휴리스틱이 아니라 제어흐름 정확성 수정이다.

한계는 코드 주석에 적어 뒀다 — `'../' in name` 은 상대경로만 막고 절대경로
(/etc/passwd)는 막지 못한다. "검사했으니 넘어간다"가 규칙이 선언한 기준이다.

결과: 파이썬 오탐 76 → 45, 정밀도 59.1% → 71.0%, F1 0.688 → 0.761,
점수 0.462 → 0.609. 재현율 82.1% 그대로. 자바는 765/54/182/571 로 변화 없다.

## 10. 사용 가이드 전면 재작성

기능이 늘어난 것에 비해 가이드가 부실했다. 91줄에 SCA·SBOM·점검 기준·제외 설정·
일괄 판정·판정 단축키·흐름 내용 필터·규칙 조정·재진단 승계·배치 진단이 통째로
빠져 있었다.

12절로 다시 썼다. 구조를 "1절만 따라 하면 첫 진단 완료 → 2절 화면 지도 → 나머지는
참조"로 바꿨다. UI 라벨과 단축키는 전부 코드에서 확인해 적었다.

쓰다 보니 렌더러도 고쳐야 했다. 가이드용 최소 마크다운이 표를 지원하지 않아
`| 항목 |` 이 날것으로 나왔고, 여러 줄 목록 항목이 끊겨 번호가 1 로 되돌아갔다.
표 렌더링과 목록 이어쓰기를 더했다.

FAQ 의 "인터넷 없이 되나요? 네" 도 정정했다 — LLM 트리아지와 SCA 조회는 외부가
필요하고, SCA 는 스냅샷으로 오프라인이 된다.

## 11. 남겨 뒀던 세 가지를 다시 본다

"실제 코드에 없는 함정"이라 미뤄 뒀던 것들을 다시 열었다. 결론부터: **분석 자체는
정당했고, 내 분류가 얕았던 부분도 있었다.**

### 불확실 표시 16.6% → 3.3%

원인은 넷이었다. 라이브러리 동작을 선언해 셋을 없앴다.

  codecs.open · subprocess.run  → propagate (리턴 객체가 입력을 들고 있다)
  xpath · elementpath.select    → block (조회 결과는 문서의 노드이지 질의문이 아니다)
  str.join                      → propagate

나머지 78건은 `thing.doSomething` 이었다. 정의가 둘인데 **둘 다 인자를 그대로
돌려주는 통과 함수**였다. 정의가 여럿이어도 요약이 전부 같으면 수신자를 몰라도
답은 하나다 — 그때만 유일 이름으로 승격한다. 이름이 흔하면(자바 코퍼스의
doSomething 은 1802개) 요약을 다 계산하는 비용이 커지므로 4개까지만 본다.

정직하게 적어 둔다: **불확실 204건 중 벤치 점수에 잡히는 것은 10건뿐**이었다.
나머지는 그 파일의 정답 유형과 다른 규칙에서 나온 것이라 채점에 안 들어간다.
점수가 아니라 검토 비용을 줄인 작업이다.

### 상수 문자열 인덱싱 — 함정이라 미뤘던 것

`"ABC"[1]` · `"ABC".charAt(1)` 을 상수 전파가 계산하게 하고, match/switch 가
`대상 == 라벨` 조건을 내게 했다. 그래야 선택자가 상수로 접힐 때 죽은 가지를 지운다.
자바의 `case 'C': case 'D':` 처럼 라벨만 있고 본문이 없는 fall-through 도 다룬다.
라벨 노드 타입을 아는 언어(자바)만 조건을 만들고, 모르는 언어는 예전처럼 분기
합집합으로 둔다.

도중에 함정 두 개를 밟았다.

* **tree-sitter 노드는 접근할 때마다 새 래퍼가 나온다.** `c is not val` 로 인덱스를
  고르려 했더니 항상 참이라 객체 자신을 인덱스로 집었다. 필드 이름과 바이트 범위로 바꿨다.
* **자바 문자열 리터럴은 `Opaque('string_literal')` 래퍼**로 오고 안쪽 조각의 원문에는
  따옴표가 없다. 리터럴 값 파서가 숫자로 오인해 상수로 접지 못했다.

### 컨테이너 — 분류가 얕았다

`lst.pop(0); bar = lst[0]` 을 "컨테이너 함정"으로 분류했는데, 직접 계산해 보니
**그 값은 실제로 오염이 맞았다.** 그 파일이 안전인 이유는 뒤따르는 `'../'` 가드였고,
9절에서 이미 고친 것이었다. 파일에 `.append(` 가 있다는 이유로 묶은 분류가 틀렸다.

실제로 남아 있던 것은 `map['keyB-15517']` 같은 **리터럴 키 첨자**였다. 이건 함정이
아니라 실무에 아주 흔하다. `map.get("키")` 에 이미 있던 키 단위 정밀도를 첨자 문법에도
줬다 — `path_of` 가 상수 인덱스를 경로에 넣는다.

여기서 균형을 두 번 잡아야 했다.

1. 슬롯만 보게 했더니 컨테이너를 통째로(또는 상수가 아닌 인덱스로) 읽는 흐름을
   놓쳐 정탐 6건이 사라졌다. 그런 읽기에는 "안에 오염된 슬롯이 있으면 딸려 나온다"를
   켠다(`slots=True`).
2. 반대로 상수 키로 특정한 읽기에는 그걸 켜면 안 된다. `d["a"]` 를 읽어도 `d["b"]` 의
   오염이 나와 키 단위 정밀도가 무의미해진다. 기존 테스트 하나가 이걸 정확히 잡아냈다.

결과: 파이썬 오탐 45 → 21, 점수 0.609 → **0.717**(재현율 82.1% 유지).
자바 오탐 182 → 100, 점수 0.692 → **0.801**(재현율 93.4% 유지).

## 12. JS·PHP 는 어떤가 — 언어 간 대조표

자바·파이썬만 정답지가 있다. 나머지 아홉 언어는 규칙만 있고 한 번도 대조된 적이 없다.
오늘 파이썬에서 고친 흐름 12종을 JS·PHP 에 그대로 물어봤다(점수가 아니라 기능 유무).

```
항목                기대     js    php     py   java
문자열 보간           취약    미탐    OK     OK     -
+= 오염 유지         취약    미탐    OK     OK   미탐
다른 키 읽기          안전    오탐   오탐     OK     -
반복 변수 바인딩        취약    미탐   미탐     OK    OK
switch 분기        취약    미탐   미탐      -    OK
상수 삼항/if(죽은 가지)  안전    오탐   오탐     OK    OK
```

**JS·PHP 는 오늘 아침의 파이썬과 같은 상태다.** 상수 전파 미작동, 반복 변수 미바인딩,
switch 분기 소실, 리터럴 키 첨자 없음 — 파이썬을 0.178 에서 0.717 로 올린 수정 대부분이
들어가 있지 않다.

여기서 하나 정정한다. `+=` 수정을 "언어 무관"이라고 적었는데 **자바에서 여전히 미탐이다.**
파이썬에만 걸린 것으로 보인다. 8절의 "자바 탐지도 4건 늘었다"는 다른 경로였을 가능성이
크고, 확인이 필요하다.

## 13. PHP 첫 점수 측정 — 무작위 수준

기능 대조만으로는 부족해 실제 정답지를 구했다. NIST SAMATE 의 PHP Vulnerability Test
Suite(Bertrand Stivalet 생성, 42,212 파일)는 라벨이 경로에 `safe`/`unsafe` 로 있다.
벤치 하네스에 세 번째 코퍼스로 넣었다 — 정답지가 CSV 가 아니라 경로에 있는 형태를 지원한다.

우리 규칙과 겹치는 CWE 여섯 종(78·79·89·95·98·601), 대상 31,824 파일로 잰다.

| 단계 | 재현율 | 정밀도 | 오탐률 | 점수 |
|---|---|---|---|---|
| 첫 측정 | 13.0% | 23.4% | 18.0% | **-0.051** |
| 소스 확장 | 32.4% | 23.4% | 45.0% | -0.126 |
| 정제 보강 | 25.2% | 28.2% | 27.2% | -0.020 |
| filter_var 제외 | 31.8% | 29.9% | 31.6% | **+0.001** |

**PHP 는 실무에 쓸 수 없다.** 0.001 은 무작위 추측과 같다. 자바 0.801 · 파이썬 0.717 과의
격차가 이 언어에 들인 작업량의 차이를 그대로 보여 준다.

### 원인 — 16개 소스 형태 중 11개가 재현율 0%

고친 것:

* `$_SESSION`·`$_ENV` 가 소스 목록에 없었다.
* 명령 출력·파일 읽기(`shell_exec`·`system`·`popen`·`proc_open`·backtick·`fgets`·
  `file_get_contents`)가 소스가 아니었다. 프로세스 밖에서 들어온 값이므로 외부 입력이다.
* `(int)$x`·`(float)$x` 캐스트가 정제로 인식되지 않았다. 숫자로 바꾼 값은 payload 를
  담을 수 없다 — 규칙과 무관한 자료형의 성질이라 규칙 YAML 이 아니라 엔진에서 끊는다
  (언어 무관).
* `mysql_real_escape_string`(구 API) 등 이스케이프 함수의 다른 이름들이 빠져 있었다.

남은 것:

* `exec($cmd, $result)` — 출력이 **by-ref 인자**로 나온다. 모델에 out-parameter 개념이 없다.
* `if (($t = fgets($h, 4096)) == false)` — **조건식 안의 대입**. 문으로 처리되지 않아
  변수가 묶이지 않는다.
* `$temp->getInput()` — 생성자에서 `$this->input = $_GET[...]` 로 담고 게터로 꺼낸다.
  **필드 흐름**이 필요하다(자바 SeparateClassRequest·파이썬 request_wrapper 와 같은 계열이지만
  이쪽은 함수 경계를 넘는 필드 대입이라 더 어렵다).

### filter_var 를 정제로 넣은 것이 해로웠다

코퍼스는 `filter_var($x, FILTER_SANITIZE_EMAIL)` 을 SQL 주입 방어로 인정하지 않는다.
**그 판단이 맞다.** 우리 모델은 함수 이름만 보고 두 번째 인자를 못 본다. A/B 로 재니
CWE_89 재현율이 32.6% → 54.3% 로 올랐다(제외했을 때). 규칙 파일에 이유를 주석으로 남겼다.

이건 벤치마크만의 문제가 아니다 — **인자를 보는 정제 모델이 없으면 `filter_var` 는 정제로
인정하면 안 된다**는 것이 실제 코드에도 그대로 적용된다.

## 이날 확인한 원칙

- **같은 뿌리의 버그가 네 번 나왔다.** `+=` · 첨자 대입 · `match/case` · `switch` —
  전부 "안전한 값 쓰기가 앞서 담긴 오염을 지운다"이다. 다른 변종이 더 있을 수 있다.
- **호출 해석은 넓히면 위험하고 좁히면 안전하다.** 전날 범위를 넓혀 취약 13건을 잃었고,
  이날 같은 파일 우선으로 좁혀 오탐 119건을 지웠다. 넓힐 때는 "모호하면 하지 않는다"는
  조건(이름 유일·수신자 변수·인자 수 일치)을 반드시 건다.
- **자바에 있는 처리가 파이썬에 없는 경우가 반복해서 나왔다.** for-each 바인딩, 상수
  전파가 그랬다. 언어를 추가할 때 정규화기 기능 대조표가 필요하다.

## 이 도구는 지금 어느 수준인가

**보조 도구로는 쓸 수 있고, 단독으로 "안전하다"를 판단하는 도구로는 아직 아니다.**

검증된 것: 자바·파이썬 데이터 흐름, 2,740파일 스캔 무파싱오류, SARIF·보고서 산출,
테스트 369건.

검증되지 않은 것:

* **11개 언어 중 2개만 측정됐다.** PHP 는 이날 처음 재서 0.001 이 나왔고, JS 는 대조표
  기준으로 PHP 와 비슷한 상태다. 나머지 일곱(Go·Ruby·Swift·C#·Kotlin·C/C++·TS)은
  대조조차 안 했다.
* **패턴 축 59개 규칙은 정답지가 아예 없다.** 실제 스캔 탐지의 다수가 이쪽이다.
* **벤치마크는 실제 코드가 아니다.** 프레임워크 라우팅·DI·ORM 이 없다. 우리 해석은
  이름 기반이라 타입 추론·동적 디스패치·import 별칭을 못 푼다.

## 남은 것

- **파이썬 미탐 24** — `pathlib.Path` 연산자 12(`exists()` sink 등록 여부 판단 필요) ·
  ConfigParser 3 · 기타 7
- **파이썬 오탐 21 / 미탐 24** — 미탐은 pathtraver 가 대부분(`pathlib.Path` 연산자).
- **자바 오탐 100 / 미탐 54** — 남은 오탐은 리스트 위치 추적(append/remove(0)/get(1))이
  큰 덩어리다. 리스트 원소의 자리를 따라가는 추상 도메인이 필요하고, 실제 코드에는
  거의 없는 형태라 하지 않는다.
- **자바 미탐 54 / 오탐 182** — 미탐은 pathtraver 14 · sqli 11 · xss 29 가 전부다.
  오탐의 대부분은 컨테이너 인덱스·상수 switch 함정이라 손대지 않는다.
- **SCA 라이선스** — 잠금파일이 값을 들고 있는 npm·composer 만 채워진다. 나머지
  생태계는 레지스트리 메타데이터 조회가 필요하다(오프라인에서는 불가).

## 하지 않기로 한 것 (유지)

- **리스트 위치 추적** (`add/add/add → remove(0) → get(1)`) — 원소의 자리를 따라가는
  추상 도메인이 필요하다. 실제 코드에 거의 없는 형태라 하지 않는다.
- **문자열 체인 추적** (`append` 후 `substring`/`split` 으로 잘라내기) — 같은 이유.

11절에서 되돌아본 것: 처음에 "상수 switch/match 선택자 접기"도 여기 넣어 뒀는데,
그건 표준적인 상수 전파였고 실제로 큰 이득이 있었다. **"실제 코드에 없는 형태"와
"표준 기법인데 이 코퍼스에서 두드러질 뿐인 것"을 구분하지 못했다.** 미루기 전에
"이 기법이 일반적으로 정당한가"를 먼저 물어야 했다.
- **벤치마크 헬퍼 이름을 규칙에 추가** — `escape_for_html` 을 정제 목록에 넣으면 오탐이
  줄지만 그건 점수 조작이다.

# 이어서 — JS·PHP 수준 올리기

## 1. 대조표부터 만들었다 (`385007a`)

점수를 재기 전에 "이 언어가 무엇을 할 수 있는가"를 물었다. 소스와 싱크만 언어별로
바꾼 **같은 모양의 최소 재현 12개**를 네 언어에 나란히 넣었다.

```
항목                기대     js    php     py   java
문자열 보간           취약    미탐    OK     OK     -
+= 오염 유지         취약    미탐    OK     OK   미탐
다른 키 읽기          안전    오탐   오탐     OK     -
반복 변수 바인딩        취약    미탐   미탐     OK    OK
switch 분기        취약    미탐   미탐      -    OK
상수 삼항/if(죽은 가지)  안전    오탐   오탐     OK    OK
```

**JS·PHP 는 그날 아침의 파이썬과 같은 상태였다.** 파이썬을 0.178 에서 0.717 로 올린
수정의 대부분이 들어가 있지 않았다. 정답지가 없어서 아무도 몰랐던 것이지, 기능이
언어별로 다를 이유는 없었다.

고친 것:

- **JS** 보간 템플릿(`` `x${p}` ``)을 Literal 로 접어 안의 오염이 사라지던 것 ·
  `augmented_assignment_expression` 미처리로 `s += p` 가 대입으로 남지 않던 것 ·
  첨자 인덱스 소실 · `for...of` 반복 변수 미바인딩 · `switch` 미처리 ·
  binary/unary/ternary 를 Opaque 로 접어 상수 전파가 죽은 가지를 못 지우던 것
- **PHP** switch 를 순차 나열로 펼쳐 뒤 case 의 안전한 대입이 앞 case 의 오염을
  지우던 것 · `foreach` 반복 변수 미바인딩 · 첨자 인덱스 소실 · 보간 없는 `"..."`
  를 상수로 인식하지 않던 것
- **C 계열** 할당 노드에서 연산자를 읽지 않고 `"="` 로 못박고 있었다. `s += p;`
  다음 줄의 `s += " safe";` 가 앞서 담긴 오염을 지웠다. 자바·C#·Go·C/C++·Swift·
  Kotlin·Ruby 가 전부 같은 코드를 쓰므로 한 줄로 일곱 언어가 고쳐졌다.

대조표는 `tests/test_conformance.py` 로 옮겼다(4언어 40건). 이제 한 언어에서 고친
것이 다른 언어에서 빠지면 테스트가 깨진다.

**여기까지의 측정: PHP 0.001 그대로.** 대조표가 잡아낸 결함은 이 코퍼스가 시험하는
지점이 아니었다. 기능 대조와 점수는 다른 것을 재고 있다 — 둘 다 필요하다.

## 2. PHP 오탐 7064건을 파일명으로 분해했다 (`c16ae49`)

SAMATE 스위트는 **파일명이 곧 변형 설명**이다.

```
CWE_89__GET__func_FILTER-CLEANING-email_filter__join-concatenation_simple_quote.php
        소스           정제                        구성
```

마디별로 묶으니 어떤 정제에서 통째로 틀리는지가 바로 나왔다.

| 오탐 | 정제 변형 | 실제 코드 |
|---|---|---|
| 1860 | `CAST-cast_int_sort_of` 계열 | `$tainted += 0;` |
| 730 | `ternary_white_list` | `$t = $t == 'safe1' ? 'safe1' : 'safe2';` |
| 900 | `func_preg_match-only_*` | `if (preg_match('/^[0-9]*$/', $t)) ...` |
| 780 | `FILTER-CLEANING-number_*` | `filter_var($t, FILTER_SANITIZE_NUMBER_INT)` |
| 550 | `whitelist_using_array` | `if (in_array($t, $legal)) ...` |

원인이 두 갈래였다.

### (a) 값의 자료형이 payload 를 담을 수 있는가

`$t == 'safe1'` 는 불리언이다. 삼항의 두 가지가 모두 리터럴인데도 **조건에 닿은
오염이 값으로 흘러나오고 있었다.** `ir.Ternary` 가 children 전체를 합집합으로
전파하고 있었기 때문이다. 조건식의 값은 then/else 중 하나이지 조건이 아니다.

같은 계열로 세 가지를 더 끊었다.

- 비교 연산자(`== === < instanceof ...`) 결과 — 언어와 무관하게 불리언이다.
- `x.length` / `.size` — 수치다. 호출 형태(`x.length()`)는 라이브러리 요약이 이미
  끊고 있었고 **속성 형태만 새고 있었다.** 이건 `env` 조회보다 **먼저** 봐야 한다:
  `x` 가 오염이면 접두 일치로 `x.length` 도 오염으로 잡히기 때문이다.
- `o.safe` 처럼 변수에 담긴 객체의 **알려진 속성 하나**를 읽을 때 객체 전체로
  되돌아가지 않는다. 되돌아가면 `o.cmd` 의 오염이 `o.safe` 로 샌다. 다만 `f().b`
  처럼 리시버가 호출인 경우는 되돌아가야 하므로, 변수에서 시작해 알려진 속성만
  타고 온 경로일 때만 끊는다(`_var_rooted`).

PHP 의 `$t += 0` 은 산술이라 결과가 수치다. 그런데 **`+` 가 문자열 결합인 언어가
있어서 엔진은 이걸 판단할 수 없다.** `ir.Binary` 에 `numeric` 표시를 두고, 언어를
아는 정규화기가 정하게 했다. PHP 는 문자열 결합이 `.` 이라 `+ - * / % ** | & ^ << >>`
가 전부 수치다. 증강 대입 `$t += 0` 은 `$t = $t + 0` 으로 펴서 같은 경로를 타게 했다.

### (b) 이름만으로는 갈리지 않는 정제

`filter_var` 는 **두 번째 인자로 안전 여부가 갈린다.** `FILTER_VALIDATE_INT` 는
주입을 막지만 `FILTER_SANITIZE_EMAIL` 은 따옴표를 그대로 남긴다. 이름만 보는
모델에서는 둘 중 하나가 반드시 틀린다 — 이전 세션에서 이걸 발견하고 `filter_var`
를 정제 목록에서 통째로 뺐는데, 그러면 숫자 필터를 쓴 안전한 코드가 전부 오탐이다.

스펙에 `requires:` 를 넣었다.

```yaml
sanitizers:
  - {callee: [filter_var], requires: [FILTER_VALIDATE_INT, FILTER_SANITIZE_NUMBER_INT, ...]}
```

인자 원문에 지정 토큰이 있을 때만 정제로 인정한다. 함께 화이트리스트·형식 검사
가드(`in_array`·`preg_match`·`ctype_*`)를 규칙별로 넣었다 — 조건문에서 정제가 경로에
걸리면 참 분기에서 검증된 것으로 보는 기존 장치(`_guarded_paths`)가 그대로 받는다.
정규식 리터럴이 리시버인 `/^[0-9]+$/.test(x)` 는 점 경로가 안 나와서 그냥 지나쳤는데,
메서드 이름으로도 보게 했다.

**측정: 0.001 → 0.246.** 오탐 7064 → 1772, 정밀도 29.9% → 63.5%.

## 4. JS 는 정답지가 없어 직접 물었다

OWASP Benchmark 에 JS 판은 없고, 라벨링된 JS 코퍼스도 찾지 못했다. 대신 **실제 노드
코드에서 흔한 형태 30개**를 최소 재현으로 만들어 물었다. 처음 결과는 15/30 실패.

| 실패 묶음 | 원인 |
|---|---|
| 구조분해 3건 | `const { x } = req.query` 의 패턴을 Opaque 로 접어 x 가 어디에도 안 묶임 |
| 콜백 4건 | `map`/`forEach`/`then` 콜백을 빈 환경으로 돌림 |
| 함수 경유 3건 | 레지스트리가 **호출 인자 안**을 안 봄 |
| 정제 4건 | `parseInt`·`Number`·정규식 `.test()`·`.length` |
| 객체 키 1건 | `{cmd: 오염, safe: 'ls'}` 의 `o.safe` 읽기 |

세 번째가 특히 컸다. 노드 웹 코드는 **라우트 전체가
`app.post('/x', function (req, res) { ... })` 안**에 들어 있다. 레지스트리는 문만
훑고 있어서 그 콜백 본문에 선언된 함수가 아예 등록되지 않았다 — 즉 **실제 익스프레스
앱에서 함수 경유 흐름이 통째로 미탐**이었다. 코퍼스가 없어서 몰랐던 것이지, 벤치마크
전용 형태가 아니라 가장 흔한 형태다. 표현식 안(호출 인자·대입 우변)의 함수 본문까지
내려가게 했다.

나머지: JS 클래스 선언이 통째로 Opaque 로 접혀 메서드가 사라지고 있던 것 · `new X()`
를 Call 로 정규화해 `new R().m()` 의 수신자 경로를 살린 것 · `map/forEach/then` 콜백의
첫 파라미터를 수신자의 오염에 묶은 것 · 객체 리터럴을 키별 슬롯으로 담은 것 ·
js 규칙의 정제 목록이 규칙당 2~4개뿐이던 것을 실제 라이브러리 이름으로 채운 것.

30/30. `tests/test_js_idioms.py` 로 고정했다.

## 6. 남은 것

- **CWE_79 미탐 2878** — 남은 PHP 미탐의 절반이다. 같은 정제 함수가 HTML 본문에서는

- **JS 정답지** — 관용구 30건은 우리가 고른 형태다. 편향을 배제하려면 외부 라벨이

## 7. 되돌아본 것

이번 세션의 교훈은 **"정답지가 없는 언어는 결함이 없는 게 아니라 안 보이는 것"**이다.
JS 는 규칙도 있고 테스트도 통과하고 있었지만, 익스프레스 라우트 안에서 함수를 부르면
흐름이 끊어졌다. 가장 흔한 형태가 가장 오래 안 보였다.

대조표(언어 간 같은 질문)와 관용구 점검(언어 안 실제 형태)은 둘 다 정답지가 아니지만,
없는 것보다 훨씬 낫다. 그리고 이 둘은 점수와 다른 것을 잡아낸다 — 대조표가 잡은 6종을
전부 고쳤을 때 PHP 점수는 0.001 에서 움직이지 않았고, 점수를 0.341 로 올린 수정은
대조표에 없던 것들이었다.

# 이어서 2 — JS/TS 우선, 그다음 코틀린·스위프트

사용자 우선순위: **PHP 는 요즘 쓰는 언어가 아니다. JS·TS 를 중점적으로, 그다음
코틀린·스위프트.** 앞 절과 같은 방식으로 갔다 — 정답지가 없으니 그 언어에서 흔한
형태를 최소 재현으로 직접 물어보고, 실패한 것만 고치고, 고칠 때마다 다시 잰다.

| 언어 | 처음 | 나중 |
|---|---|---|
| TypeScript | 13/30 실패 | 0 |
| Kotlin | 6/16 실패 | 0 |
| Swift | 6/14 실패 | 0 |

커밋 `2d222cd`. 테스트 439 → 499개.

## 1. TypeScript — 파라미터 하나가 전부였다

TS 관용구 30개를 물어보니 캐스팅(`as`, `<T>`, `satisfies`)·논널 단언·제네릭 호출·
옵셔널 체이닝은 전부 통과했다. Opaque 로 접어도 자식의 오염이 합집합으로 전파되니
타입 문법은 애초에 방해가 안 된다.

**실패한 13개 중 8개가 한 가지 원인이었다.** TS 파라미터는
`required_parameter{pattern, type}` 로 감싸여 오는데, 정규화기가 노드 텍스트를
그대로 이름으로 쓰고 있었다.

```
ir.Param(name="v: string")      # ← 이러면 인자 전파가 영영 안 걸린다
```

요약은 "파라미터 이름"으로 환경을 만든다. 이름이 `v: string` 이면 본문의 `v` 와
절대 이어지지 않는다. **즉 타입을 쓴 함수는 전부 프로시저간 분석에서 빠져 있었다.**
TS 에서 타입을 안 쓰는 함수는 없으므로, 사실상 TS 는 프로시저간 분석이 없었다.

나머지: export/namespace/abstract class 를 뚫고 들어가기, 생성자 파라미터
프로퍼티(`constructor(private readonly cmd: string)`), NestJS 의 `@Query`·`@Body`
파라미터 데코레이터를 소스로 인정하기(자바 Spring 의 `@RequestParam` 을 위해 이미
있던 장치를 그대로 썼다 — 컨트롤러는 호출자가 없어 요약으로는 절대 안 잡힌다).

## 2. 생성자 → 필드 → 메서드 (공용)

TS 에서 마지막까지 남은 두 개가 이거였다.

```ts
class Svc {
  constructor(private readonly cmd: string) {}
  run() { cp.exec(this.cmd); }
}
new Svc(req.query.x).run();
```

**파이썬·자바·PHP·TS 넷 다 이 형태를 통째로 놓치고 있었다.** 서비스 클래스가
생성자로 받은 값을 필드에 두고 메서드에서 쓰는, 가장 흔한 OOP 모양이다.

요약에 수신자 축을 넣었다.

| 필드 | 뜻 |
|---|---|
| `taints_self` | 이 파라미터가 객체의 필드로 들어가는가 (생성자·세터) |
| `self_sink_paths` | 객체가 오염이면 이 메서드가 안에서 싱크에 닿는가 |
| `self_returns` | 객체가 오염이면 리턴도 오염인가 (게터) |
| `is_ctor` | 이 호출이 곧 객체 생성인가 |

필드를 구분하지 않는 **객체 단위 근사**다. 컨테이너를 통째로 오염으로 보는 기존
모델과 같은 기준이라 새 종류의 부정확이 아니다.

여기 오기까지 막고 있던 것 셋:

1. **생성자를 이름으로 찾을 수 없었다.** `constructor`/`__init__`/`__construct`
   라는 이름으로는 `new Svc(x)` 가 정의에 닿지 못한다. 클래스 이름으로 등록한다
   (자바·C# 은 이미 이름이 클래스명이라 표시만 단다).
2. **`this` 가 Opaque 로 접히고 있었다.** JS 와 C 계열 모두. `this.cmd` 의 경로가
   아예 만들어지지 않으니 필드에 담긴 오염을 추적할 수가 없다.
3. **PHP 의 `new X(...)` 는 인자 컨테이너가 필드가 아니다.** 인자가 비어 있어
   생성자에 값이 전달된 적이 없는 것처럼 보였다.

비용을 줄이려고 수신자 실행은 **함수가 this/self 를 실제로 쓸 때만** 한다. 안 그러면
함수마다 실행이 한 번씩 더 늘어난다. 코틀린·스위프트는 필드를 `this.` 없이 쓰므로
원문 바이트가 아니라 IR 을 본다(정규화기가 `this.` 를 붙여 준다).

## 3. Kotlin

- **`"ls $p"`** — 이 문법은 중괄호 없는 보간을 노드로 노출하지 않는다. 조각이
  `string_content('$')` + `string_content('p')` 로 쪼개져 온다. 직접 읽어 식별자를
  살렸다. (`"ls ${p}"` 는 `interpolation` 노드라 원래 됐다 — 같은 코드인데 중괄호
  유무로 결과가 갈리고 있었다.)
- **주 생성자 프로퍼티** `class Svc(val cmd: String)` — 선언과 대입이 한 줄에 있어
  생성자 함수 자체가 없다. 만들어 준다.
- **필드를 `this.` 없이 쓴다.** 클래스의 필드 이름을 알고 본문에 들어가, 그 이름의
  식별자를 `this.<이름>` 으로 바꾼다.
- **후행 람다** `a.forEach { v -> ... }` 가 인자 컨테이너 **밖**에 있어 인자로 세지
  않고 있었다. 게다가 람다 본문도 컨테이너 없이 바로 자식이라, 인자로 세고 나서도
  몸통이 빈 함수가 됐다. 둘 다 고쳐야 이어진다.
- 이름 없는 람다의 `it`, `let`·`also`·`apply` 스코프 함수
- **`true`/`false` 를 identifier 로 준다** — 리터럴로 두지 않으면 상수 전파가
  `if (false)` 의 죽은 가지를 못 지운다(오탐).

## 4. Swift

- **`s += p` 의 좌변이 `directly_assignable_expression` 로 한 겹 감싸여 있어**
  경로가 안 만들어지고 대입 자체가 사라졌다. 같은 이유로 switch 분기의 대입도
  전부 사라지고 있었다.
- `if let q = e` / `guard let g = e` 의 이름 묶기
- `for v in a` 반복 변수 바인딩
- 클로저 파라미터가 한 겹 안쪽(`lambda_function_type`)에 있다

## 5. 측정

```
자바   0.801 → 0.801   (변화 없음)
파이썬 0.717 → 0.717   (변화 없음)
PHP    0.341 → 0.338   (오탐 +302, 재현율 동일)
```

PHP 가 조금 내려간 이유는 분명하다. 코퍼스의 안전 변형에 **객체를 만든 뒤 메서드가
필드를 정제하는** 형태가 있다.

```php
$s = new Sanitize($tainted);
$s->sanitize();          // 여기서 필드가 씻긴다
$q = $s->getData();      // 우리 모델은 "객체가 오염" 이라고만 안다
```

객체 단위 근사로는 "필드가 씻겼다"를 표현할 수 없다. 필드 단위로 올리면 풀리지만
별개 작업이고, 실제 코드에서 이 기능이 잡아 주는 흐름이 훨씬 많다고 보고 유지했다.

## 6. 되돌아본 것

앞 절의 교훈이 그대로 반복됐다 — **정답지가 없는 언어는 결함이 없는 게 아니라
안 보이는 것.** 이번에는 더 극단적이었다.

- TS 는 타입을 쓴 함수가 전부 프로시저간 분석에서 빠져 있었다. TS 에서 타입을 안
  쓰는 함수는 없다. 즉 **TS 지원은 이름만 있었다.**
- 코틀린은 `"$p"` 와 `"${p}"` 의 결과가 갈리고 있었다. 같은 코드다.
- 생성자 → 필드 → 메서드는 네 언어 전부에서 미탐이었는데, 벤치마크 두 개(자바·
  파이썬)가 마침 그 형태를 안 쓴다는 이유로 여태 드러나지 않았다.

관용구 점검은 정답지가 아니다. 우리가 고른 형태라 편향이 있다. 그래도 **없는 것보다
훨씬 낫고, 점수와 다른 것을 잡아낸다** — 이번에 고친 것 중 벤치마크 점수를 움직인
것은 하나도 없다. 자바·파이썬은 소수점까지 그대로였다.

## 7. 남은 것 (갱신)

- **필드 단위 객체 모델** — 위의 `sanitize()` 형태. 지금은 객체 단위라 정제를 못 본다.
- **CWE_79 미탐 2878** — 출력 문맥에 따라 답이 갈리는 형태. taint 만으로는 불가.
- **JS/TS·코틀린·스위프트 정답지** — 관용구 30/30/14 는 우리가 고른 형태다. 공개된
  라벨 코퍼스를 못 찾았다.
- **성능** — 자바 코퍼스(2740 파일) 전체 스캔이 **20분 17초**다. 원인을 재봤다:
  직전 커밋(`c16ae49`)을 별도 워크트리에 꺼내 같은 코퍼스로 돌리니 **17분 17초**였고,
  현재 트리에서 수신자 실행만 꺼도 18분 9초였다. 즉 이번 변경분은 +17% 이고, 나머지
  17분은 **원래 그랬다** — 요약 고정점 반복 자체가 무겁다. 별도로 프로파일링해야 한다.
  (파일 수가 이 정도인 실제 프로젝트는 드물지만, 그래도 느리다.)

## 4. 고친 것 (`f792a90`)

### (a) 소스 패턴 — 프레임워크 하나만 알고 있었다

koa 의 `ctx.*`, gin/echo 의 `c.*`, httplib 의 `req.get_param_value`, C# 의 `args` 와
프로세스 출력을 넣었다. 전부 YAML 데이터다.

### (b) 참조 출력 인자 — 리턴이 아니라 인자로 결과가 나온다

```c
char buf[256];
fread(buf, 1, n, stdin);                    // outparam: 그 자체가 입력
snprintf(cmd, sizeof(cmd), "ls %s", buf);   // outcopy: 오염을 cmd 로 옮긴다
system(cmd);
```

C 계열 입력 API 가 **전부** 이 모양이라 리턴값만 보는 모델로는 통째로 미탐이었다.
어떤 호출의 몇 번째 인자가 출력인지는 규칙이 선언한다. PHP 의 `exec($cmd, $out)` 도
같은 장치로 잡힌다 — 앞 세션에서 "남은 것"에 적어 둔 항목이 여기서 같이 풀렸다.

c/standalone 재현율 10.8% → 66.4%, cpp/standalone 1.0% → 58.5%.

### (c) 거부하고 돌아가는 검증

```js
if (!["ls","cat","date"].includes(data)) { res.status(403).json(...); return; }
childProcess.execSync("echo " + data);     // 여기서는 검증된 값
```

오탐 표본을 뽑아 세어 보니 안전 변형의 다수가 이 형태였다. 기존 `validators`
장치(파이썬 경로 조작의 `'..'` 검사용으로 만든 것)를 언어별 허용 목록·형식 검사
이름으로 채웠다. **JS 오탐률 45.1% → 18.7%.**

C++ 에는 넣었다가 **뺐다** — 오탐을 하나도 못 줄이고(83건 그대로) 재현율만
44.0% → 39.5% 로 깎았다. 측정하지 않았으면 좋아진 줄 알았을 것이다.

### (d) 그 밖에

- **루비 `unless`** 가 조건문으로 안 잡혀 가드가 통째로 사라지고 있었다.
- **루비 블록(`do...end`)** 이 인자 컨테이너 밖에 있어 시나트라 라우트 본문이 분석에서
  빠졌다 — 앞 절의 코틀린 후행 람다와 **똑같은 문제**다. 같은 결함이 언어를 건너
  반복된다는 것을 또 확인했다.
- **`std::getenv` 는 `getenv` 다.** 이름공간을 규칙에 두 번 적게 하면 목록이 두 배가
  되고 하나는 반드시 빠진다 — 매칭에서 `::` 앞을 뗀다.
- **`execv`/`posix_spawn` 은 셸을 거치지 않는다.** 인자 배열에 값이 들어가는 것은
  명령 주입이 아니라 인자 주입이다. 프로그램 경로 자리만 sink 로 봤다(C 오탐률
  54.0% → 32.8%). 대신 `argument_injection` 유형은 그만큼 덜 잡는다 — 맞바꾼 것이다.

# 이어서 5 — Go 분해

`8b4bfef`. 규칙 있는 언어 중 최하였던 Go(0.044)를 파고 문서를 다시 맞췄다.

## 1. 원인은 셋, 그중 둘은 전 언어 문제였다

미탐 336건을 추리니 소스는 정상 인식되고 있었다 — 흐름이 **뒤에서** 끊겼다. 실패
형태 11개를 최소 재현으로 만들어 하나씩 확인했다.

### (a) 클로저가 빈 환경으로 실행되고 있었다

```go
v := c.GetHeader("X")
go func() { DB.Query("S " + v) }()      // v 가 오염인 줄 모른다
```

중첩 함수를 실행할 때 바깥 환경을 넘기지 않았다. Go 의 고루틴·defer·맵 안 함수
리터럴이 전부 이 모양이고, **JS 의 콜백도 같다.**

고치자 여섯 스위트가 같이 올랐다.

| 스위트 | 전 | 후 |
|---|---|---|
| javascript/express | 0.375 | 0.445 |
| typescript/express_ts | 0.376 | 0.431 |
| javascript/koa | 0.362 | 0.402 |
| ruby/rails | 0.373 | 0.388 |
| typescript/nestjs | 0.342 | 0.380 |
| ruby/sinatra | 0.342 | 0.355 |

**한 코퍼스에서 찾은 결함이 다른 코퍼스의 점수를 올린다** — 그 수정이 코퍼스에
맞춘 것이 아니라는 가장 좋은 증거다. Go 를 안 쟀으면 JS 도 그만큼 낮은 채였다.

### (b) 내가 어제 넣은 소스가 통째로 무시되고 있었다

어제 소스를 추가할 때 `(pattern, object)` 가 이미 있으면 **건너뛰었다.** Go 는 `c`·
`ctx` 가 원래 있었던 탓에 gin 용 속성이 하나도 안 들어갔고, `c.Request.Body` 와
`c.FormFile` 이 소스로 잡히지 않았다.

`_matches_source("c.FormFile")` 를 직접 불러 보고서야 알았다. **어제 "고쳤다"고
적은 것이 실제로는 반만 적용된 상태였다.** 같은 객체면 속성 목록을 합치도록 고쳤고
js·cpp·csharp 도 같이 다시 합쳤다.

### (c) Go 도 참조 출력 인자가 핵심이었다

```go
json.NewDecoder(c.Request.Body).Decode(&q)   // 오염이 수신자에 있다
c.ShouldBindJSON(&q)                          // 호출 자체가 입력이다
json.Unmarshal(body, &q)                      // arg 1 이 출력이다
```

C 계열에 넣은 outparam/outcopy 를 확장했다. outcopy 가 **수신자**도 보게 하고,
`&q` 처럼 주소를 넘기는 형태를 한 겹 벗겼다. 앞 절의 C 작업이 그대로 재활용됐다.

## 2. 오탐: 조회표를 키로 쓴 검사

```go
allowed := map[string]bool{"asc": true, "desc": true}
if !allowed[data] { 거부; return }
exec.Command("sh", "-c", "echo "+data)
```

기존 `validators` 는 **조건문 텍스트의 토큰**으로 판단하는데, 여기엔 호출이 없다.
값이 **표의 키로 조회됐고** 그 분기가 돌아가 버렸다면 미리 정해진 집합의 원소다 —
언어 무관한 형태라 토큰 없이도 인정하게 했다. 컨테이너를 읽는 형태(`data[i]`)와는
구별한다: 그쪽은 첨자가 아니라 베이스가 오염 경로다.

Go 오탐 192 → 148.

## 4. 하지 않은 것 — 파생값 가드

Go 오탐의 45%(87건)가 이 형태다.

```go
parsed, _ := url.Parse(data)
if parsed.Hostname() == "metadata.google.internal" { 거부; return }
http.Get(data)                                       // ← data 를 쓴다
```

오염값에서 **파생된 값**을 검사해 거부하면 원본도 검증된 것으로 볼지의 문제다.
우리는 트레이스로 provenance 를 들고 있으므로 구현은 가능하다. 하지만 투영
(hostname)을 검사했다고 원본 전체를 안전하다고 보는 것은 일반적으로 건전하지 않고,
전 언어에 영향을 준다. **크고 위험한 수정이라 따로 측정해서 정한다.**

## 6. 되돌아본 것

어제 "고쳤다"고 쓴 소스 추가가 **반만 적용돼 있었다.** 스크립트가 조용히 건너뛴 것을
검증하지 않았기 때문이다. `_matches_source` 를 직접 불러 확인하는 데 30초가 걸렸고,
그걸 어제 했다면 Go 는 어제 올랐을 것이다.

**"적용했다"와 "적용되어 동작한다"는 다르다.** 데이터를 고쳤을 때는 고친 데이터를
읽는 함수를 직접 불러 봐야 한다. 테스트가 통과한다는 것은 기존 동작이 안 깨졌다는
뜻일 뿐, 새로 넣은 것이 걸린다는 뜻이 아니다.
