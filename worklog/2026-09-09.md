## 1. 검수 결함 4건 (`1cb050f`)

전날 만든 확인·알림 창을 스스로 검수해 네 가지를 찾았다. 셋은 브라우저에서 재현했다.

1. **파괴적인 확인 창에서 Enter 가 '취소' 포커스를 무시했다.** 캡처 단계에서 Enter 를
   가로채 `preventDefault` 하고 무조건 '확인'으로 해결했다. 포커스된 버튼이 활성화될
   기회가 없으니 "취소에 포커스를 둬 오입력을 막는다"는 장치가 아무 역할도 못 했다 —
   스캔 삭제 창에서 Enter 한 번이면 지워졌다. Enter 는 브라우저가 포커스된 버튼을 누르게
   두고 Esc 만 다룬다.
2. **창이 떠 있는데 다시 열면 앞의 Promise 가 영영 풀리지 않았다.** `resolver` 를 그냥
   덮어써서 앞 호출의 `.then` 이 실행되지 않았다. 앞의 것을 '아니오'로 닫고 연다.
3. **표 보기의 빈 체크박스 열 헤더를 누르면 정렬이 깨졌다.** 정렬 핸들러를 모든 `th` 에
   걸어 `data-col` 이 없는 헤더가 `ws.sort` 를 `undefined` 로 만들었고, 그 값이
   localStorage 에 남아 새로고침해도 죽어 있었다.
4. **일괄 의견이 기존 개별 의견을 말없이 덮어썼다.** 메모는 이력이 없어 복구할 수 없다.
   기본은 건드리지 않고, 덮어쓰려면 호출부가 `overwrite` 를 명시해야 한다. 확인 창이
   대상 중 이미 의견이 적힌 건수를 보여주고 체크박스를 띄운다(기본 꺼짐).

## 4. 파이썬 미탐 — for 와 with (`86e78f1`)

미탐 69건을 분류해 둘을 고쳤다. 둘 다 파이썬에서 아주 흔한 형태다.

1. **`for` 반복 변수가 순회 대상의 오염을 이어받지 못했다**(13건).
   `for name in request.form.keys(): open(name)` 이 통째로 미탐이었다. 반복 변수가
   어디서도 묶이지 않았다. 자바 정규화기에는 이미 있던 처리라 파이썬만 빠져 있었다.
2. **`with` 문의 컨텍스트 식이 사라졌다**(14건). `with open(사용자경로) as fd:` 에서
   `open(...)` 호출 자체가 IR 에서 없어져 sink 검사를 아예 못 했다. try 와 같은 묶음으로
   본문만 펼치고 있었기 때문이다.

결과: 재현율 48.5% → 67.9%, 점수 0.178 → 0.292.

## 5. 파이썬에 상수 전파가 걸리지 않고 있었다 (`8de266b`)

`constfold` 는 "컴파일 시점에 결과가 정해지는 분기를 접는다"고 적혀 있고 자바에서는
실제로 동작한다. 그런데 파이썬 정규화기가 연산자와 조건식을 Opaque 로 접어 버려 접을
근거가 IR 에 남지 않았다. taint 전파는 같지만 실행되지 않는 가지가 그대로 오염으로 남는다.

`binary_operator`·`boolean_operator`·`comparison_operator` → `ir.Binary`,
`unary_operator`·`not_operator` → `ir.Unary`, `conditional_expression` → `ir.Ternary`.
파이썬은 `참값 if 조건 else 거짓값` 순서라 constfold 가 기대하는 `[조건, 참, 거짓]`으로
바꿔 넣는다. `a < b < c` 처럼 연산자가 여럿인 비교는 접지 않는다.

보수적인 기존 기준은 실측으로 확인했다 — 조건이 거짓으로 접히면 취약 가지가 남고,
조건이 변수면 접지 않으며, 한 스코프에서 두 번 대입된 이름도 접지 않는다.

결과: 정밀도 52.6% → 57.6%, 오탐 82 → 67, 점수 0.292 → 0.363.

## 6. 유일 이름 해석 · self 자리 · self.request (`8cbaca4`)

파이썬 미탐을 다시 분류하니 **request 래퍼 객체 경유 21건**이 최대였다.

```python
wrapped = helpers.separate_request.request_wrapper(request)
param = wrapped.get_form_parameter("BenchmarkTest00272")
```

세 가지가 겹쳐 있었다.

1. **수신자가 변수라 정의를 못 찾는다.** 전날 이 범위를 넓혔다가 취약 13건을 미탐으로
   만든 전례가 있어 조심스럽다. 그래서 **이름의 정의가 프로젝트 전체에 하나뿐일 때만**
   해석한다. 실측: `get_form_parameter` 1개, `getTheParameter` 1개, 반면
   **`doSomething` 은 자바 코퍼스에 1802개** — 모호하면 자동으로 걸러진다.
   여기에 수신자가 단순 변수일 것과 인자 수가 맞을 것을 추가 조건으로 걸었다.
2. **파이썬 메서드 요약의 파라미터 자리가 한 칸씩 밀려 있었다.** `obj.m(a)` 는 인자가
   `[a]` 뿐인데 요약은 `self` 를 파라미터 0 으로 센다. 프로시저간 판정이 통째로 어긋난다.
   요약에 `implicit_self` 를 담고 수신자 호출이면 자리를 맞춘다.
3. **`self.request.form` 이 소스로 안 잡혔다.** 요청 객체를 인스턴스에 담아 두는 것은
   Django 클래스 뷰·자바 컨트롤러에서 표준에 가깝다. `self`/`this`/`cls` 한 겹만 벗기고
   매칭한다. 기존 이름 기반 매칭과 같은 방식이고, 같은 클래스의 `get_safe_value` 는
   여전히 소스가 아닌 것으로 확인했다.

파이썬 결과: 재현율 67.9% → 82.1%, 점수 0.363 → 0.420, 미탐 43 → 24.

자바에서 xss 재현율이 86.2% → 77.6% 로 떨어졌다. 이름만 유일하다고 이어 붙이면
수신자가 라이브러리 객체인 호출까지 엉뚱한 요약을 씌운다. 1번에 조건 두 개를 더 걸었다
— 수신자가 단순 변수일 것, 인자 수가 맞을 것(수신자 호출이면 self 한 자리 제외).
그러자 xss 재현율이 88.2% 로 회복됐고 오탐은 29건 그대로였다. 원래(86.2%)보다도 높다.

자바 결과: 재현율 87.2% → 93.4%, 정밀도 80.2% → 80.8%, 점수 0.649 → 0.692.
파이썬은 안전장치 전후가 같다(82.1%, 0.420) — 래퍼 해석이 그대로 산다.

## 7. 파이썬 오탐 85건 분해 → 바인딩 파라미터 질의 (`미커밋`)

오탐을 흐름 트레이스로 분류했다.

| 건수 | 원인 | 성격 |
|---|---|---|
| ~24 | 조기 반환 가드 `if '../' in bar: return` 후 사용 | 실제 코드에 흔함 |
| 19 | 컨테이너 왕복 | 함정 |
| 19 | `match/case` 상수 선택 | 함정(문자열 인덱싱 필요) |
| **9** | **바인딩 파라미터 질의** | **진짜 결함** |
| 2 | 슬라이스/split | 함정 |

9건이 `sqli` 오탐 전부였다.

```python
cur.execute(sql, (bar,))     # sql 은 플레이스홀더, bar 는 바인딩 → SQLi 정석 방어
```

인자를 전부 검사하니 **방어를 제대로 한 코드가 오탐**이 됐다. `SinkPattern.arg` 가
정확히 이걸 위한 필드인데 쓰지 않고 있었다. `arg: 0` 으로 질의문만 본다 — 문자열
연결로 만든 진짜 취약점은 첫 인자에서 그대로 잡힌다. `extra()` 는 `select=`·`where=`
키워드로 받아 자리를 특정할 수 없어 제외했다.

자바에도 같은 구조가 있어 함께 적용했다(`executeUpdate(sql, new int[]{1,2})`,
`queryForObject(sql, Integer.class, bar)`). **자바 수치는 변하지 않았다** — 이 코퍼스의
안전 변형이 뒤 인자로 오염값을 넘기지 않기 때문이다. 실제 코드에서는 유효한 수정이다.

파이썬 결과: 오탐 85 → 76, 정밀도 56.4% → 59.1%, 점수 0.420 → 0.462.

남은 최대 덩어리는 **조기 반환 가드 ~24건**이다. `if 검증실패: return` 은 실제 코드에
아주 흔하고 함정이 아니다. 다만 "어떤 검사가 충분한가"는 규칙이 선언해야 하는 문제라
(지금 `sanitizers` 는 호출만 인식한다) 설계 판단이 필요해 남겨 뒀다.

## 8. SCA 오프라인 조회 (`미커밋`)

국내 기반시설 진단은 망분리가 흔한데, SCA 는 OSV.dev 조회가 필요했다. 세 가지를 고쳤다.

1. **"취약점 없음"과 "조회 못 함"을 구분한다.** 예전에는 둘 다 빈 결과였고 문구로만
   단서를 달았다. 망분리 환경에서 돌리면 산출물에 "알려진 취약점 없음"으로 적히는데,
   그건 확인하지 않은 값이다. `query_osv` 가 실패 시 `{}` 대신 `None` 을 돌려주게 해
   호출부가 "미수행"으로 보고한다.
2. **로컬 스냅샷 조회** — `--sca-db DIR` 또는 `CPGUARD_OSV_DIR`. `<dir>/PyPI.zip`(받은
   zip 그대로)과 `<dir>/PyPI/*.json`(풀어 둔 것)을 모두 읽는다. zip 은 스트리밍으로 읽어
   메모리를 묶는다. 스냅샷이 있으면 네트워크보다 먼저 쓴다 — 의존성 목록이 밖으로
   나가지 않는다.
3. **`cpguard osv-sync`** — 인터넷 되는 곳에서 미리 받는 명령. 이 명령만 네트워크를 쓴다.

버전 판정은 ① `versions[]` 명시 목록 ② 없으면 범위(`introduced`/`fixed`/`last_affected`)
③ GIT 범위나 파싱 불가면 **판정 보류**로 세어 요약에 건수를 적는다. 정식 semver 파서는
두지 않았다 — 생태계마다 규칙이 다르고, 애매하면 보류가 산출물에 잘못 쓰는 것보다 낫다.

회귀 테스트 4개를 더했다. 그 중 하나는 "조회 차단을 취약점 없음으로 쓰면 안 된다"를
직접 검증한다.

## 9. 조기 반환 가드 — 규칙이 "무엇이 검증인가"를 선언한다

파이썬 오탐의 최대 덩어리였다. 형태는 둘뿐이었다.

    if '../' in bar:                      15건 — 경로 조작 거부
        return 오류
    if not bar.startswith("'") or ...:    16건 — 따옴표 형식 검증
        return 오류

정제 *함수*를 부르지 않고 값의 형태만 확인해 거부하는 코드라 기존 sanitizers(호출
이름 목록)로는 잡히지 않았다. 무엇을 검증으로 인정할지는 유형마다 다르므로 규칙이
선언하게 했다(`validators:`). 경로 조작은 `'..'` 포함 검사, 코드 주입은
`startswith`/`endswith` 형식 검사다.

두 조건이 모두 맞을 때만 적용한다.
  1. 참 분기가 반드시 돌아간다(return).
  2. 조건에 규칙이 선언한 검증 표시가 있고, 그 조건이 오염 경로를 언급한다.

그래서 `if not b: return` 처럼 무관한 가드나 다른 변수를 검사하는 가드는 여전히
탐지한다(최소 재현 6건으로 확인).

부수 효과로 **참 분기가 return 하면 그 분기의 상태를 이어붙이지 않게** 됐다. 이쪽은
휴리스틱이 아니라 제어흐름 정확성 수정이다.

한계는 코드 주석에 적어 뒀다 — `'../' in name` 은 상대경로만 막고 절대경로
(/etc/passwd)는 막지 못한다. "검사했으니 넘어간다"가 규칙이 선언한 기준이다.

결과: 파이썬 오탐 76 → 45, 정밀도 59.1% → 71.0%, F1 0.688 → 0.761,
점수 0.462 → 0.609. 재현율 82.1% 그대로. 자바는 765/54/182/571 로 변화 없다.

## 10. 사용 가이드 전면 재작성

기능이 늘어난 것에 비해 가이드가 부실했다. 91줄에 SCA·SBOM·점검 기준·제외 설정·
일괄 판정·판정 단축키·흐름 내용 필터·규칙 조정·재진단 승계·배치 진단이 통째로
빠져 있었다.

12절로 다시 썼다. 구조를 "1절만 따라 하면 첫 진단 완료 → 2절 화면 지도 → 나머지는
참조"로 바꿨다. UI 라벨과 단축키는 전부 코드에서 확인해 적었다.

쓰다 보니 렌더러도 고쳐야 했다. 가이드용 최소 마크다운이 표를 지원하지 않아
`| 항목 |` 이 날것으로 나왔고, 여러 줄 목록 항목이 끊겨 번호가 1 로 되돌아갔다.
표 렌더링과 목록 이어쓰기를 더했다.

FAQ 의 "인터넷 없이 되나요? 네" 도 정정했다 — LLM 트리아지와 SCA 조회는 외부가
필요하고, SCA 는 스냅샷으로 오프라인이 된다.

## 11. 남겨 뒀던 세 가지를 다시 본다

"실제 코드에 없는 함정"이라 미뤄 뒀던 것들을 다시 열었다. 결론부터: **분석 자체는
정당했고, 내 분류가 얕았던 부분도 있었다.**

### 불확실 표시 16.6% → 3.3%

원인은 넷이었다. 라이브러리 동작을 선언해 셋을 없앴다.

  codecs.open · subprocess.run  → propagate (리턴 객체가 입력을 들고 있다)
  xpath · elementpath.select    → block (조회 결과는 문서의 노드이지 질의문이 아니다)
  str.join                      → propagate

나머지 78건은 `thing.doSomething` 이었다. 정의가 둘인데 **둘 다 인자를 그대로
돌려주는 통과 함수**였다. 정의가 여럿이어도 요약이 전부 같으면 수신자를 몰라도
답은 하나다 — 그때만 유일 이름으로 승격한다. 이름이 흔하면(자바 코퍼스의
doSomething 은 1802개) 요약을 다 계산하는 비용이 커지므로 4개까지만 본다.

정직하게 적어 둔다: **불확실 204건 중 벤치 점수에 잡히는 것은 10건뿐**이었다.
나머지는 그 파일의 정답 유형과 다른 규칙에서 나온 것이라 채점에 안 들어간다.
점수가 아니라 검토 비용을 줄인 작업이다.

### 상수 문자열 인덱싱 — 함정이라 미뤘던 것

`"ABC"[1]` · `"ABC".charAt(1)` 을 상수 전파가 계산하게 하고, match/switch 가
`대상 == 라벨` 조건을 내게 했다. 그래야 선택자가 상수로 접힐 때 죽은 가지를 지운다.
자바의 `case 'C': case 'D':` 처럼 라벨만 있고 본문이 없는 fall-through 도 다룬다.
라벨 노드 타입을 아는 언어(자바)만 조건을 만들고, 모르는 언어는 예전처럼 분기
합집합으로 둔다.

도중에 함정 두 개를 밟았다.

* **tree-sitter 노드는 접근할 때마다 새 래퍼가 나온다.** `c is not val` 로 인덱스를
  고르려 했더니 항상 참이라 객체 자신을 인덱스로 집었다. 필드 이름과 바이트 범위로 바꿨다.
* **자바 문자열 리터럴은 `Opaque('string_literal')` 래퍼**로 오고 안쪽 조각의 원문에는
  따옴표가 없다. 리터럴 값 파서가 숫자로 오인해 상수로 접지 못했다.

### 컨테이너 — 분류가 얕았다

`lst.pop(0); bar = lst[0]` 을 "컨테이너 함정"으로 분류했는데, 직접 계산해 보니
**그 값은 실제로 오염이 맞았다.** 그 파일이 안전인 이유는 뒤따르는 `'../'` 가드였고,
9절에서 이미 고친 것이었다. 파일에 `.append(` 가 있다는 이유로 묶은 분류가 틀렸다.

실제로 남아 있던 것은 `map['keyB-15517']` 같은 **리터럴 키 첨자**였다. 이건 함정이
아니라 실무에 아주 흔하다. `map.get("키")` 에 이미 있던 키 단위 정밀도를 첨자 문법에도
줬다 — `path_of` 가 상수 인덱스를 경로에 넣는다.

여기서 균형을 두 번 잡아야 했다.

1. 슬롯만 보게 했더니 컨테이너를 통째로(또는 상수가 아닌 인덱스로) 읽는 흐름을
   놓쳐 정탐 6건이 사라졌다. 그런 읽기에는 "안에 오염된 슬롯이 있으면 딸려 나온다"를
   켠다(`slots=True`).
2. 반대로 상수 키로 특정한 읽기에는 그걸 켜면 안 된다. `d["a"]` 를 읽어도 `d["b"]` 의
   오염이 나와 키 단위 정밀도가 무의미해진다. 기존 테스트 하나가 이걸 정확히 잡아냈다.

결과: 파이썬 오탐 45 → 21, 점수 0.609 → **0.717**(재현율 82.1% 유지).
자바 오탐 182 → 100, 점수 0.692 → **0.801**(재현율 93.4% 유지).

## 12. JS·PHP 는 어떤가 — 언어 간 대조표

자바·파이썬만 정답지가 있다. 나머지 아홉 언어는 규칙만 있고 한 번도 대조된 적이 없다.
오늘 파이썬에서 고친 흐름 12종을 JS·PHP 에 그대로 물어봤다(점수가 아니라 기능 유무).

```
항목                기대     js    php     py   java
문자열 보간           취약    미탐    OK     OK     -
+= 오염 유지         취약    미탐    OK     OK   미탐
다른 키 읽기          안전    오탐   오탐     OK     -
반복 변수 바인딩        취약    미탐   미탐     OK    OK
switch 분기        취약    미탐   미탐      -    OK
상수 삼항/if(죽은 가지)  안전    오탐   오탐     OK    OK
```

**JS·PHP 는 오늘 아침의 파이썬과 같은 상태다.** 상수 전파 미작동, 반복 변수 미바인딩,
switch 분기 소실, 리터럴 키 첨자 없음 — 파이썬을 0.178 에서 0.717 로 올린 수정 대부분이
들어가 있지 않다.

여기서 하나 정정한다. `+=` 수정을 "언어 무관"이라고 적었는데 **자바에서 여전히 미탐이다.**
파이썬에만 걸린 것으로 보인다. 8절의 "자바 탐지도 4건 늘었다"는 다른 경로였을 가능성이
크고, 확인이 필요하다.

## 13. PHP 첫 점수 측정 — 무작위 수준

기능 대조만으로는 부족해 실제 정답지를 구했다. NIST SAMATE 의 PHP Vulnerability Test
Suite(Bertrand Stivalet 생성, 42,212 파일)는 라벨이 경로에 `safe`/`unsafe` 로 있다.
벤치 하네스에 세 번째 코퍼스로 넣었다 — 정답지가 CSV 가 아니라 경로에 있는 형태를 지원한다.

우리 규칙과 겹치는 CWE 여섯 종(78·79·89·95·98·601), 대상 31,824 파일로 잰다.

| 단계 | 재현율 | 정밀도 | 오탐률 | 점수 |
|---|---|---|---|---|
| 첫 측정 | 13.0% | 23.4% | 18.0% | **-0.051** |
| 소스 확장 | 32.4% | 23.4% | 45.0% | -0.126 |
| 정제 보강 | 25.2% | 28.2% | 27.2% | -0.020 |
| filter_var 제외 | 31.8% | 29.9% | 31.6% | **+0.001** |

**PHP 는 실무에 쓸 수 없다.** 0.001 은 무작위 추측과 같다. 자바 0.801 · 파이썬 0.717 과의
격차가 이 언어에 들인 작업량의 차이를 그대로 보여 준다.

### 원인 — 16개 소스 형태 중 11개가 재현율 0%

고친 것:

* `$_SESSION`·`$_ENV` 가 소스 목록에 없었다.
* 명령 출력·파일 읽기(`shell_exec`·`system`·`popen`·`proc_open`·backtick·`fgets`·
  `file_get_contents`)가 소스가 아니었다. 프로세스 밖에서 들어온 값이므로 외부 입력이다.
* `(int)$x`·`(float)$x` 캐스트가 정제로 인식되지 않았다. 숫자로 바꾼 값은 payload 를
  담을 수 없다 — 규칙과 무관한 자료형의 성질이라 규칙 YAML 이 아니라 엔진에서 끊는다
  (언어 무관).
* `mysql_real_escape_string`(구 API) 등 이스케이프 함수의 다른 이름들이 빠져 있었다.

남은 것:

* `exec($cmd, $result)` — 출력이 **by-ref 인자**로 나온다. 모델에 out-parameter 개념이 없다.
* `if (($t = fgets($h, 4096)) == false)` — **조건식 안의 대입**. 문으로 처리되지 않아
  변수가 묶이지 않는다.
* `$temp->getInput()` — 생성자에서 `$this->input = $_GET[...]` 로 담고 게터로 꺼낸다.
  **필드 흐름**이 필요하다(자바 SeparateClassRequest·파이썬 request_wrapper 와 같은 계열이지만
  이쪽은 함수 경계를 넘는 필드 대입이라 더 어렵다).

### filter_var 를 정제로 넣은 것이 해로웠다

코퍼스는 `filter_var($x, FILTER_SANITIZE_EMAIL)` 을 SQL 주입 방어로 인정하지 않는다.
**그 판단이 맞다.** 우리 모델은 함수 이름만 보고 두 번째 인자를 못 본다. A/B 로 재니
CWE_89 재현율이 32.6% → 54.3% 로 올랐다(제외했을 때). 규칙 파일에 이유를 주석으로 남겼다.

이건 벤치마크만의 문제가 아니다 — **인자를 보는 정제 모델이 없으면 `filter_var` 는 정제로
인정하면 안 된다**는 것이 실제 코드에도 그대로 적용된다.

## 이날 확인한 원칙

- **같은 뿌리의 버그가 네 번 나왔다.** `+=` · 첨자 대입 · `match/case` · `switch` —
  전부 "안전한 값 쓰기가 앞서 담긴 오염을 지운다"이다. 다른 변종이 더 있을 수 있다.
- **호출 해석은 넓히면 위험하고 좁히면 안전하다.** 전날 범위를 넓혀 취약 13건을 잃었고,
  이날 같은 파일 우선으로 좁혀 오탐 119건을 지웠다. 넓힐 때는 "모호하면 하지 않는다"는
  조건(이름 유일·수신자 변수·인자 수 일치)을 반드시 건다.
- **자바에 있는 처리가 파이썬에 없는 경우가 반복해서 나왔다.** for-each 바인딩, 상수
  전파가 그랬다. 언어를 추가할 때 정규화기 기능 대조표가 필요하다.

## 이 도구는 지금 어느 수준인가

**보조 도구로는 쓸 수 있고, 단독으로 "안전하다"를 판단하는 도구로는 아직 아니다.**

검증된 것: 자바·파이썬 데이터 흐름, 2,740파일 스캔 무파싱오류, SARIF·보고서 산출,
테스트 369건.

검증되지 않은 것:

* **11개 언어 중 2개만 측정됐다.** PHP 는 이날 처음 재서 0.001 이 나왔고, JS 는 대조표
  기준으로 PHP 와 비슷한 상태다. 나머지 일곱(Go·Ruby·Swift·C#·Kotlin·C/C++·TS)은
  대조조차 안 했다.
* **패턴 축 59개 규칙은 정답지가 아예 없다.** 실제 스캔 탐지의 다수가 이쪽이다.
* **벤치마크는 실제 코드가 아니다.** 프레임워크 라우팅·DI·ORM 이 없다. 우리 해석은
  이름 기반이라 타입 추론·동적 디스패치·import 별칭을 못 푼다.

## 남은 것

- **파이썬 미탐 24** — `pathlib.Path` 연산자 12(`exists()` sink 등록 여부 판단 필요) ·
  ConfigParser 3 · 기타 7
- **파이썬 오탐 21 / 미탐 24** — 미탐은 pathtraver 가 대부분(`pathlib.Path` 연산자).
- **자바 오탐 100 / 미탐 54** — 남은 오탐은 리스트 위치 추적(append/remove(0)/get(1))이
  큰 덩어리다. 리스트 원소의 자리를 따라가는 추상 도메인이 필요하고, 실제 코드에는
  거의 없는 형태라 하지 않는다.
- **자바 미탐 54 / 오탐 182** — 미탐은 pathtraver 14 · sqli 11 · xss 29 가 전부다.
  오탐의 대부분은 컨테이너 인덱스·상수 switch 함정이라 손대지 않는다.
- **SCA 라이선스** — 잠금파일이 값을 들고 있는 npm·composer 만 채워진다. 나머지
  생태계는 레지스트리 메타데이터 조회가 필요하다(오프라인에서는 불가).

## 하지 않기로 한 것 (유지)

- **리스트 위치 추적** (`add/add/add → remove(0) → get(1)`) — 원소의 자리를 따라가는
  추상 도메인이 필요하다. 실제 코드에 거의 없는 형태라 하지 않는다.
- **문자열 체인 추적** (`append` 후 `substring`/`split` 으로 잘라내기) — 같은 이유.
