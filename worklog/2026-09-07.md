## 1. 코드 검수에서 나온 결함 6건 (`af7f608`)

셋은 성격이 같다 — **보안 도구가 진단 대상 때문에 다치는 경로**.

- **zip 해제가 헤더를 믿었다.** 크기·압축률 검사는 아카이브가 신고한 값을 보는데, 실제
  해제는 `copyfileobj` 로 무제한 스트리밍했다. 1KB 라고 적고 100GB 로 부푸는 항목이
  모든 검사를 통과해 디스크를 채운다. 복사하면서 실제 바이트를 세어 같은 상한을 다시 건다.
- **mask 없는 규칙이 다른 규칙의 개인정보를 흘렸다.** `_masked_line` 이 자기 매치만
  가려서, 주민번호와 사설 IP 가 같은 줄에 있으면 `infra.private-ip` 결과가 원문 줄을
  그대로 실었다. 줄 단위로 필요한 마스킹을 한 번 계산해 그 줄을 인용하는 모든 finding 에 적용.
- **CSV·xlsx 수식 인젝션.** 스캔 대상에서 온 파일 경로·소스가 이스케이프 없이 셀에
  들어가, `=cmd|'/c calc'!A1.js` 같은 파일명이 발주처 엑셀에서 실행된다. `csv_safe()` 추가.

나머지 셋:

- `sink.arg` 가 범위 밖이면 "인자 미지정"과 같게 처리돼 **모든 인자**를 검사했다 →
  규칙이 명시적으로 제외한 자리에서 오탐.
- `set_audit` 이 index 범위를 검사하지 않아 실재하지 않는 항목만큼 집계가 어긋날 수 있었다.
- 스캔 목록이 행마다 `findings_json` 블롭을 파싱했다 → `FindingRow` 인덱스로 집계.

## 2. 감사 상태가 숫자를 움직인다 (`9238808`, `8123b83`)

판정해도 대시보드가 그대로였다. 개념은 이미 두 군데 있었는데(리포트 화면의 인라인
`open_count`, 합본 보고서의 최종 조치대상) **정작 사람이 보는 화면에만 없었다.**

`Scan.open_count` / `open_severity_counts` / `audit_summary` 로 모델에 올리고 프로젝트 홈·
작업대 헤더·스캔 목록이 쓴다. **탐지 총계는 그대로 둔다** — 스캔이 찾은 사실이고,
줄어드는 건 "남은 일"이다.

이어서 작업대 헤더를 **새로고침 없이** 움직이게 했다. 전체 재계산이 아니라 판정이
열림↔닫힘을 넘을 때만 ±1 하므로 대량 모드에서도 정확하다.

> 함정: 추가한 `SEV_ORDER` 상수가 기존 선언과 충돌해 **작업대 스크립트 전체가 로드 시점에
> 죽었다**(이슈 0건). 파이썬 테스트로는 안 잡힌다 — 브라우저 콘솔에서 확인.

## 3. 5GB 프로젝트가 1,762건으로 쪼개진 문제 (`1889d9f`)

`_split_batch_zip` 이 "안에 zip 이 하나라도 있으면 배치"로 판정했다. yarn PnP 의
`.yarn/cache/*.zip` 을 프로젝트로 착각한 것이다. 판정 기준을 **"zip 들만 있을 때"** 로
바꿨다 — zip 아닌 파일이 섞여 있으면 소스가 든 단일 프로젝트다.

## 4. 진단 워크플로

- **판정 승계** (`9b9448f`) — 지문(규칙+파일+공백 정규화한 sink 코드)이 같으면 직전
  스캔의 감사 상태·의견을 가져온다. 재점검에서 지난번 오탐을 다시 판정하지 않는다.
  작업대 헤더에 `판정 승계 N` 을 띄운다 — 조용히 넘어온 숫자는 아무도 믿지 않는다.
- **일괄 판정** (`af6c51e`) — 필터로 좁힌 결과 전체를 한 번에. 대량 모드에서는 목록이
  잘려 있어 "보이는 전부"가 말과 달라지므로 막았다.
- **흐름 내용 필터** (`430c1ac`) — 추적 경로 안의 호출·변수를 조건으로 건다(전체/source/

- **판정 이력·저장하고 다음·유사 이슈 그룹** (`0dac5df`) — 유사 그룹 키는 LLM 트리아지가

  판정이 정확히 그 묶음에 걸린다.

## 6. 브라우저 실측

파이썬 테스트가 못 보는 것들이라 실제로 띄워서 확인했다.

- 판정 즉시 반영: `조치대상 7 · CRITICAL 1 HIGH 6` → 오탐 → `6 · HIGH 6` → 감사 해제 → 복귀
- 일괄 판정: HIGH 필터 6건 → 오탐 → 조치대상 7→1, 서버 저장 확인
- 흐름 필터: 4건 중 `sanitize`/`escape` 거친 2건만 선별 → 일괄 오탐 → 4→2
- 진단 중단: 4,000파일 스캔을 extract 중 중단 → `cancelled`, Scan 레코드 미생성
- 복귀 띠: `/scan/running` 이 진행 중 진단을 보고하고, 끝나면 사라짐

이 과정에서 JS 문자열 리터럴이 깨져 스크립트가 죽은 사례가 **두 번** 나왔다.
UI 변경은 브라우저로 열어보기 전까지 완료가 아니다.

## 7. 6절까지의 남은 것을 그대로 처리

앞 절 끝에 적어둔 다섯 항목을 이어서 끝냈다.

### 7.1 합본 보고서에 양식 적용 (`53462a2` 계열)

`consolidated_report()` 가 양식을 받는다. 표지 제목·머리말·로고와 절 on/off 가 단일
스캔 보고서와 같게 동작하고, 스캔이 하나뿐인 합본에는 분석 대상 현황과 제외·기준
부록을 붙인다(여러 건이면 스캔마다 설정이 달라 한 장에 못 싣는다).

### 7.2 경로 민감도 — 검증하는 분기만 오염을 뺀다

`if (is_numeric($x)) { query($x); }` 처럼 **값을 바꾸지 않고 검사만 하는 코드**가 실제로
가장 흔한 오탐 원인이다. 조건이 검증한 경로를 참 분기에서만 지운다.

> 함정: 부정(`!is_numeric($z)`)은 노드 타입으로 안 드러난다 — PHP 정규화에서 Unary 가
> 아니라 Opaque 로 온다. 처음 구현은 **위험한 쪽 분기를 조용히 안전하다고 판정했다.**
> 원본 바이트를 봐서 부정을 걸러낸다.

OWASP Benchmark 점수는 그대로다(0.392 / F1 0.689). 그 코퍼스는 검증이 아니라 **변환**으로
안전하게 만드는 케이스가 대부분이라 이 경로를 타지 않는다. 수치가 안 움직였다고
기능을 되돌리지는 않았다 — 실제 코드에서 줄어드는 오탐이 목적이다.

### 7.3 프레임워크 진입점을 소스로 (`be93eb6`)

Spring 컨트롤러가 통째로 미탐이었다. 파라미터는 프레임워크가 채우므로 **호출자가 없고**,
우리 함수 요약은 "호출 인자에서 오염이 들어오는" 경로만 본다. IR 을 찍어보니 어노테이션
자체가 정규화 단계에서 버려지고 있었다.

- `ir.Param.annotations` 추가, 정규화기가 파라미터 어노테이션 이름을 모은다.
- 스펙에 소스 패턴 `annotation` 추가. Spring 9종(`@RequestParam`·`@PathVariable`·
  `@RequestBody` 등)과 ASP.NET Core 5종(`[FromQuery]`·`[FromBody]` 등)을 등록.
- 어노테이션 **없는** 파라미터는 그대로 둔다. 전부 소스로 보면 내부 헬퍼가 오탐 밭이 된다.

> Kotlin 은 어노테이션이 `parameter` 의 자식이 아니라 앞 형제(`parameter_modifiers`)로
> 붙는다. Java·C# 만 보고 끝냈으면 Kotlin 만 조용히 미탐으로 남았다.

### 7.4 모바일 점검 기준 — 5번은 "오버플로우"였다 (`c473d61`)

국가법령정보센터의 「모바일 전자정부 서비스 관리 지침」 [별표 3] 원문으로 대조했다.
빠져 있던 5번은 **오버플로우(정수형, 메모리 버퍼)**, 그리고 목록 끝의 **26번 소스코드
난독화 미적용**도 통째로 없었다. 24개 → 26개.

26번은 코드에서 찾는 약점이 아니라 빌드 산출물의 성질이라 대응 CWE 가 없다. 매핑을
비워 두고 항목만 싣는다 — 없는 CWE 를 억지로 붙이면 점검표가 거짓말을 한다.
목록이 확인됐으므로 초안 표시를 뗐다(기능 자체는 남긴다).

### 7.5 국내 기준 확장 — 설계단계 기준 (`ea148eb`)

같은 [별표 3]의 앞 절이 **설계단계 보안설계 기준 20개**다(입력데이터 검증 10 · 보안기능
8 · 에러처리 1 · 세션통제 1). 구현단계 49개와 짝을 이루는데 우리에겐 뒤쪽만 있었다.

설계서를 보는 항목이라 CWE 매핑이 없고, `coverage()` 가 전부 **'진단 대상 아님'** 으로
표시한다. 정적 분석이 확인하지 않은 항목을 양호로 찍지 않기 위한 기존 판정을 그대로
쓴 것이다.

대조하는 김에 구현단계 49개도 원문과 맞췄다 — 항목·분류는 그대로 일치했고, 표기만
정정했다(`오버플로` → `오버플로우`, `해시함수` → `해쉬함수`). 근거 문서 표기도 가이드
이름에서 별표 조문으로 바꿨다. 발주처가 대조하는 건 별표다.

# SPARROW 대조에서 나온 네 가지 격차 처리

상용 SAST(SPARROW) 구조를 대조하면서 나온 항목 네 개를 모두 처리했다.

## 9. 규칙 개명이 판정 승계를 끊는 문제

재진단 승계 지문(`fp`)은 `rule_id | 파일 | sink 코드` 로 만든다. 규칙 id 를 바꾸는 순간
과거 진단의 오탐·보류 판정이 전부 끊기고, 모든 탐지가 신규로 보인다. 2·3차 진단에서
진단원이 다시 판정해야 한다는 뜻이라 실제 결함이다.

SPARROW 는 `SAST.SW.JAVA.1454` 같은 불변 숫자키를 두고 옛 이름을 `legacyKey` 로 보존한다.
숫자키 자체를 따라가지는 않았다 — `java.sqli` 도 안 바꾸는 한 불변키다. 없던 것은
**개명 경로**다.

`report/finding.py` 에 `RULE_ALIASES`(옛 id → 현재 id), `canonical_rule_id()`,
`fingerprint()`, `stored_fp()` 를 두었다. 저장된 탐지 dict 는 이미 `steps[-1].code` 를
들고 있어, 규칙이 개명됐으면 옛 스캔의 지문을 현재 이름으로 다시 계산한다. 지문 포맷과
저장 데이터는 그대로다 — 마이그레이션이 없다.

지문을 비교하는 곳은 두 군데였고 둘 다 같은 결함이었다: `_carry_over_audit`(판정 승계)와
`Scan.compare_with`(신규/해결). 둘 다 `stored_fp()` 로 통일했다.

개명 이력은 규칙 YAML 의 `legacy_ids:` 로도 쓸 수 있다. 로더가 읽어 `RULE_ALIASES` 에
싣는다.

## 10. 조치 권고가 규칙의 36%를 덮지 못하고 있었다

`_rule_key()` 는 rule_id 접미사 문자열로 조치 유형을 찾는데, 규칙 137개 중 **50개**가
어디에도 걸리지 않아 일반 문구로 떨어지고 있었다. `vendor.*` 18종, `*.deserialization`,
`*.ldap-injection`, `*.xpath-injection`, `cpp.buffer-overflow`, `web.*`, `infra.*`,
`hygiene.*` 전부였다. 발주처 산출물에서 조치 방안이 규칙과 무관한 문장이 되는 문제다.

조치 유형 16종을 한글·영문 양쪽에 추가하고, 접미 매칭으로 안 잡히는 규칙 18개는
`_EXPLICIT_KEY` 에 명시 매핑했다. `vendor.` 접두는 전부 하드코딩된 비밀정보로 본다.
미매핑은 0이 되었고, `tests/test_remediation_map.py` 가 새 규칙이 들어올 때 실패로 잡는다.

같이 **취약한 코드 예시**를 유형별로 넣었다(`VULN_EXAMPLE`). 조치 권고에 고친 코드만
있으면 개발자가 자기 코드에서 무엇을 찾아야 하는지 모른다. 고치기 전 모습과 고친 모습을
쌍으로 싣는다. 코드라 번역하지 않고 한/영 공용으로 쓴다. PDF 카드와 Word 블록 양쪽에
반영했다.

## 11. 사용자 규칙 조정 — 옵션 스키마가 아니라 YAML 오버레이

SPARROW 는 규칙별 사용자 설정 항목을 약 2,900개 둔다(금지 함수 목록, 임계값, 허용 도메인).
같은 수의 옵션을 만들지는 않았다. **규칙 YAML 이 이미 그 설정 파일이기 때문이다.**

`load_rules()` 에 오버레이를 붙였다. `~/.cpguard/specs/*.yml`(또는 `CPGUARD_SPECS`)에 같은
`id` 의 yml 을 두면 동봉 규칙 위에 겹쳐진다. 리스트 키(sources·sinks·sanitizers·languages)는
이어붙이고 — 사내 검증 함수를 sanitizer 로 인정하거나 금지 함수를 추가하는 용도다 —
스칼라 키는 사용자 값이 이긴다(severity 하향). 동봉 목록을 통째로 버리려면 `replace: true`.
새 `id` 면 사용자 규칙이 그대로 추가된다.

오버레이는 결과를 바꾸므로 진단 로그와 `scan_config_json.tuned_specs` 에 남긴다.
재현할 수 없는 진단은 산출물이 되지 못한다.

## 12. SCA — 오픈소스 컴포넌트 취약점 점검

없던 축이다. 정적 분석은 우리가 쓴 코드만 보는데, 국내 진단 사업에서 실제로 요구되는
항목 하나는 "쓰고 있는 오픈소스에 알려진 취약점이 있는가" 이고 그건 의존성 목록에 있다.

`cpguard/sca.py`. 잠금파일 7종을 읽는다 — `requirements.txt`(`==` 고정만),
`package-lock.json`(v1/v2/v3), `pom.xml`(리터럴 버전만), `go.mod`, `Gemfile.lock`,
`composer.lock`, `packages.config`. 취약점 조회는 **OSV.dev** 다. 자체 취약점 DB 를 들고
있지 않은 이유는 OSV 가 npm·PyPI·Maven·Go·RubyGems·Packagist·NuGet 를 한 스키마로
무료 제공하기 때문이다. 오프라인 진단이 요구되면 그때 스냅샷을 미러한다.

결과는 일반 `Finding` 으로 바꾼다(`sca.vulnerable-dependency`, CWE-1395,
A06:2021). 기존 보고서·SARIF·검토 화면·판정 승계가 전부 그대로 처리한다.

**기본은 꺼져 있다.** 조회는 패키지 이름·버전을 외부(api.osv.dev)로 보낸다. 진단 대상의
의존성 목록은 그 자체로 정보다. CLI 는 `--sca`, 웹은 업로드 화면의 체크박스이고 문구에
전송 사실을 적었다. 수행 여부와 요약은 `scan_config_json.sca_note` 에 남는다 — 안 한
점검을 한 것처럼 보이면 안 된다.

XML 잠금파일은 신뢰할 수 없는 입력이다. `ElementTree` 는 내부 엔티티를 실제로 전개하므로
(billion laughs 확인함), `<!DOCTYPE`/`<!ENTITY` 가 있는 XML 은 읽지 않고 5MB 상한을 둔다.
`defusedxml` 의존성을 늘리는 것보다 싸고 확실하다.

라이선스는 잠금파일이 이미 들고 있는 것만 읽는다(npm·composer). 나머지 생태계까지 보려면
레지스트리 메타데이터 조회가 따로 필요한데 그건 다음이다.

## 13. 검증 — OSV 실조회에서 결함 두 개가 나왔다

`lodash 4.17.15` 로 실조회를 돌리고 나서야 드러난 것들이다. 오프라인 테스트만으로는
안 잡혔다.

**1) 취약점 상세 조회가 전부 실패하고 있었다.** `/v1/vulns/<id>` 는 GET 만 받는데
POST 로 보내고 있었다. 예외를 삼키고 `{"id": vid}` 로 넘어가는 폴백이 있어서 오류 없이
결과만 비어 나왔다 — CVE 번호도, 수정 버전도, CVSS 등급도 없이 전부 `medium` 이었다.
`_call()` 로 바꿔 payload 가 없으면 GET 을 보낸다.

**2) 같은 CVE 가 두 번 실렸다.** OSV 는 하나의 CVE 를 서로 다른 GHSA 권고 여러 건으로
준다(lodash 는 6건 중 2쌍이 중복이었다). 산출물에 같은 취약점이 두 번 나가면 진단원이
손으로 걸러야 한다. 컴포넌트+CVE 로 묶고 등급은 최댓값, 수정 버전은 합집합을 쓴다.
수정 버전이 여럿이면 유지보수 계열이 여럿이라는 뜻이므로 문구도 그렇게 적는다
(`4.17.23, 4.18.0 중 하나 이상`).

수정 후 실조회 결과 — 6건 → 중복 제거 4건, CVE·요약·등급·수정 버전 전부 정상:

    [high]   CVE-2020-8203    Prototype Pollution        조치: 4.17.19 이상
    [high]   CVE-2021-23337   Command Injection          조치: 4.17.21, 4.18.0 중 하나 이상
    [medium] CVE-2020-28500   ReDoS                      조치: 4.17.21 이상
    [medium] CVE-2025-13465   Prototype Pollution        조치: 4.17.23, 4.18.0 중 하나 이상

테스트 340개 통과(신규 27개: 개명 승계 3 · 조치 매핑 3 · 오버레이 6 · SCA 15).

## 14. 남은 것

- 라이선스 점검 — PyPI·Maven·NuGet 는 레지스트리 메타데이터 조회 필요
- 오프라인 진단용 OSV 스냅샷 미러
- Django·Express 진입점(라우팅=source, 템플릿=sink)

# 새 기능에 맞춘 검토 화면 정리

기능을 붙이고 화면을 열어 보니 새 축이 UI 어디에도 없었다. 네 가지를 고쳤고 그중 둘은
UI 문제가 아니라 데이터가 틀리는 문제였다.

## 15. 새 유형이 필터에도 라벨에도 없었다

`dependency` 는 새 category 인데 작업대의 유형 필터 옵션에 없어서 골라낼 수 없었고,
`CAT_LABEL` 에도 없어 상세 패널과 유형별 그룹에 `dependency` 라는 원문이 그대로 나왔다.
프로젝트 홈의 종류 셀렉트도 서버가 준 원문을 그대로 쓰고 있었다. 양쪽에 '오픈소스
컴포넌트' 를 추가하고, 프로젝트 홈에도 같은 라벨 표를 두었다.

## 16. SCA 탐지는 규칙 id 가 라벨로 쓸모없다

목록에 `sca.vulnerable-dependency · CWE-1395 · package-lock.json:7` 이 세 줄 연속으로
찍혔다. 모든 SCA 탐지가 같은 규칙이라 라벨이 전부 같다. 구분되는 것은 컴포넌트와 CVE 다.

`matched_value` 에 `lodash@4.17.15 · CVE-2021-23337` 형태로 싣고, 목록·트리·표에서
`dependency` 인 탐지만 이 값을 제목으로 쓴다. 상세 패널의 `탐지값 (마스킹)` 도 이 경우엔
`컴포넌트` 로 바꿨다 — 마스킹된 비밀정보가 아니라 패키지 이름이다.

## 17. 코드 뷰어가 잠금파일 첫 줄로 보내고 있었다

json·xml 파서는 줄 번호를 주지 않아 전부 1 로 두고 있었는데, 검토 화면은 그 줄로 이동한다.
진단원이 파일에서 해당 컴포넌트를 직접 찾아야 했다. 원문을 한 번 훑어 그 컴포넌트가 적힌
줄을 찾는다(`_line_of`). package-lock·composer.lock·pom.xml·packages.config 에 적용했다.

## 18. SCA 를 껐다 켜면 신규/해결이 거짓말을 했다

`compare_with` 는 지문 기준이라, SCA 를 끈 채 재진단하면 오픈소스 취약점이 전부
**'해결됨'** 으로 잡힌다. 조치하지 않은 것을 조치했다고 쓰는 산출물이 된다.

수행 여부를 `scan_config.sca` 에 기록하고, 두 스캔의 수행 여부가 다르면 오픈소스 항목을
비교에서 뺀다. 함께 본 축만 비교한다.

## 19. 진단 수행 조건이 화면에 없었다

규칙 오버레이 적용 목록과 SCA 수행 여부를 산출물(`scan_config_json`)에만 남기고 화면에는
안 보여주고 있었다. 두 진단의 결과가 왜 다른지 진단원이 찾을 방법이 없다. 프로젝트 홈에
'최근 진단 수행 조건' 절을 넣어 조정된 규칙 목록과 SCA 요약을 보여준다. 조정이 없으면
`~/.cpguard/specs/` 로 조정하는 방법을 안내한다 — 설정 기능은 알려주지 않으면 없는 것과 같다.

## 20. 검증

임시 DB(`CPGUARD_HOME` 분리, 사용자 실제 DB 미접촉)에 SCA 결과를 심고 서버를 띄워
프로젝트 홈과 검토 화면을 눈으로 확인했다. 잠금파일 줄 번호는 실제 파서로 9·13 이
나오는 것을 확인했다.

테스트 345개 통과(신규 5개: SCA 비교 축 3 · 수행 조건 렌더 2).

# 부록 E — 오픈소스 컴포넌트 목록(SBOM)

## 21. 컴포넌트 목록을 산출물에 싣는다

SCA 를 붙이면서 컴포넌트 목록을 만들어 놓고 버리고 있었다. "어떤 오픈소스를 쓰는가" 는
취약점과 별개로 요구되는 산출물이고, 취약점이 0건이어도 목록 자체가 점검했다는 근거다.

`sca.scan()` 이 컴포넌트 목록도 돌려주게 하고(`sbom_rows()`), 스캔 설정 블롭에
`sbom` 으로 남긴다. PDF·Word 보고서에 **부록 E. 오픈소스 컴포넌트 목록** 을 추가했다 —
생태계·컴포넌트·버전·라이선스·취약점 수. 합본 보고서에도 같이 붙는다.

정렬은 취약점이 있는 컴포넌트부터다. 발주처가 먼저 보는 것이 그쪽이다. 모노레포는
컴포넌트가 수천 개라 표가 보고서를 삼키므로 500행에서 자르고, 자른 만큼은 표 아래에
전체 건수로 밝힌다.

라이선스는 잠금파일이 값을 들고 있는 생태계(npm·composer)만 채워지고 나머지는 `-` 다.
PyPI·Maven·NuGet 까지 보려면 레지스트리 메타데이터 조회가 따로 필요하다.

테스트 348개 통과(신규 3개 + 기존 PDF 보고서 테스트에 부록 E 검증 추가).
