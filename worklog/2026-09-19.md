## C# 오탐 프로브 — 필터 형태별로 갈라 원인 셋, 수정 둘, 보류 둘

CWE-89 때 방식으로 **안전(manifest good) 케이스를 필터 형태(F_)별로 버킷** → 샘플 스캔.
오탐이 형태에 집중돼 있었다: 22 `invalid_filenames_chars_path` 69% · `good_regex_parent_dir`
44%, 78 `…semi-colon_path` 67%, 90 `invalids_ldap_char` 47%, 91 `xml_encode` 19%,
89 `func_preg_match-only_numbers` 31%. 한 겹 더(소스별) 가르니 **모든 버킷에서 hardcoded
만 0%, args·readline·shell 은 ~100%** — 즉 그 정제 형태를 전혀 못 알아보는 것이지
소스나 싱크 문제가 아니다. 규칙 5종의 sanitizer/validator 목록이 전부 같은 보일러플레이트
인 것도 확인.

**형태 세 가지**
- (A) `Regex r = new Regex(..); v = r.Replace(x, "")` — 22·78. 문자 삭제.
- (B) `Match m = r.Match(x); if(!m.Success){v="";}else{v=x;}` — 89. 검증→분기.
- (C) StringBuilder 수동 이스케이프(switch/Append · `.Replace("&","&amp;")` 체인) — 90·91.

**(A) 는 측정이 '넣지 말라'고 했다.** 메모리 내 규칙 변형으로 같은 층화 표본(312)을
재니 `Replace` 를 정제로 보면 점수 중립(0.715 → 0.716): FP −4, **TP −5**. 손실 내역이
핵심 — 같은 Replace 필터가 cwe_22/78 에선 good, cwe_89/90/91 에선 **bad** 로 라벨돼
있다(문자 삭제는 SQL·LDAP·XPath 엔 부족). 규칙별(22·78 만)로 넣으면 0.733 이지만
"문자 삭제 = 정제" 는 의미상 약한 판단이라 정책 보류. `Regex.Replace` 는 수신자 타입
추적이 없어 `r.Replace` 로만 보인다(bare `Replace` 는 `s.Replace(" ","")` 까지 정제로
봐 미탐 위험).

**(B) 는 엔진 확장(커밋 74e4445).** `_defaulted_path` 가 else 있으면 즉시 None 이었다.
else 를 허용하되 else 가 넣는 값이 검사된 값(또는 `_derived_origins` 로 닿는 원본)일 때만,
then 은 오염 없는 값. 검사 소스로 부정된 validator 토큰 멤버(`!m.Success`)를 추가.
`Success` 는 **csharp.sqli 에만** — 5종에 다 넣었더니 cwe_78/90 정탐 3건을 잃었다
(같은 코드를 SARD 가 거기선 bad 로 라벨: '숫자만' 검사를 명령·LDAP 엔 불충분으로 봄).
무엇을 검증으로 인정할지는 싱크마다 달라 규칙이 선언한다 — 그 설계 이유를 몸으로 배움.

**루프 안 변형(커밋 5bccd09)**: 남은 preg_match 오탐은 `do{…}while` · `while((1==1)){…break;}`
로 감싼 것. `_run_loop` 이 0회 실행 경로로 루프 전 env 를 항상 합류시켜 검증 전 값이
되살아났다. `ir.Loop.at_least_once`(do_statement) + 상수참 조건이면 합류 제외.

**덤으로 잡은 진짜 결함(커밋 c2b4d73)**: 루프 테스트의 **양성 대조군이 미탐**으로 나왔다.
추적하니 cfam `_decl` 의 C# 폴백이 초기값 후보에서 identifier 를 전부 빼 `string v = x;`
가 Assign 조차 안 만들어지고 있었다 — C# 선언 복사가 통째로 미탐. SARD 는 `= null`
선언 뒤 대입이라 안 드러났다. **음성 항목만 있는 테스트는 공짜로 통과한다 — 대조군을
반드시 둔다**(이번엔 그 규율이 결함을 잡았다).

**(C) 보류**: 이름이 없는 진짜 인코더. StringBuilder 수신자 변이(`text.Replace(...)` 는
반환값 미사용)를 정제로 보려면 "수신자를 씻는 정제" 의미가 필요하다. 다음 후보.

**측정(층화 표본 312, HEAD a0a9a01 → 세 커밋 후)**: 0.715 → **0.751**(FP 28 → 23,
TP 162 그대로). Java 200 지문 동일. 회귀 549 통과. 공식 전량은 아래.

**공식 전량 1차(루프까지, goto 전)**: 0.687 → 0.716 (정밀도 88.4→90.4%, 오탐률 15.6→
12.6%), cwe_89 0.631→0.678 (FP 1,224→816). 그런데 **cwe_89 TP 9,936→9,912(−24)** —
표본에선 0 이었던 손실. 열어 보니 전부 preg_match 변형 1-15: `goto Skip;` 으로 검증
블록을 통째로 건너뛰는 bad 케이스. 엔진이 goto 를 모르고 선형으로 읽어 죽은 코드의
if/else 가 오염을 씻었다(그전엔 if/else 를 못 알아봐 우연히 맞았음).

**전방 goto(커밋 511cd36)**: `_run` 에서 `goto L;` 시점 env 를 `L:` 에서 합류 — "건너뛸 수
있다". C# 의 `Skip: {}` 는 정규화 뒤 맨 Ident 라 원문 `이름:` 으로 판별. 24건 전부 회복,
표본 0.751 유지, Java 지문 동일, 회귀 552.

**교훈 둘**: ① 표본이 0 손실이어도 전량은 다르다 — 수정이 닿는 버킷은 전량으로 재고
잃은 것은 이름까지 연다(24건이 한 변형에 몰려 있어 원인이 바로 보였다). ② "우연히
맞던 것"은 정확도가 올라갈 때 드러난다 — 검증을 알아보기 시작하자 goto 무시가 결함이
됐다. 한 곳을 정확하게 만들면 그 앞뒤의 근사가 새로 시험대에 오른다.

**공식 전량 최종(커밋 511cd36 상태, 6분 50초)**: 전체 **0.687 → 0.717** — 재현율 84.3%
