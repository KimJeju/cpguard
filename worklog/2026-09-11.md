그래서 답을 코드에 미리 박지 않고, 플래그 뒤에 구현해 **15개 스위트를 전부 다시 재고**

## 1. 먼저 오탐을 세었다

어제 남긴 메모에는 "Go 오탐의 45%(87건)"라고 적혀 있었다. 숫자를 믿지 않고 다시 뽑았다.

```
cloud_ssrf_metadata 31 · ssrf 28 · redirect 28   ← 87건
sqli 18 · genericcmdi 14 · argument_injection 14 · cmdi 6 · xss 9
```

전체 148건 중 87건이므로 **59%** 였다(45% 는 다른 분모로 센 값이다). 세 유형이 전부
같은 형태다.

```go
data := c.Query("id")
parsedURL, err := url.Parse(data)
_host := parsedURL.Hostname()
if _host == "metadata.google.internal" { return }   // 검사는 투영에
http.Get(data)                                      // 사용은 원본으로
```

취약 쌍둥이(00157)를 같이 열어 본 것이 중요했다 — **가드가 아예 없다**. 즉 이 코퍼스에서
가드를 인정해도 재현율을 잃을 구조가 아니다. 이걸 먼저 확인하지 않으면 "오탐이 줄었다"가
"미탐이 늘었다"의 다른 이름일 수 있다.

## 2. 걸림돌이 둘이었다

거부 조건의 실제 모양이 세 가지인데, 규칙의 `validators` 토큰(`Contains`·`MatchString`·
`Atoi` …)에 **하나도 걸리지 않았다**.

| 형태 | 예 |
|---|---|
| 리터럴 동등비교 | `_host == "metadata"` |
| 조회표 | `!allowed[parsedURL.Hostname()]` |
| IP 분류 | `ip.IsPrivate() \|\| ip.IsLoopback()` |

그래서 파생 추적만 넣었으면 **0건** 고쳐졌다. 검사 인정 범위와 파생 추적이 같이 가야
한다는 걸 IR 을 찍어 보고서야 알았다. 추측으로 한쪽만 만들었으면 "구현했는데 점수가
안 오른다"로 하루를 버렸을 것이다.

## 3. 파생 추적에는 새 자료구조가 필요 없었다

env 는 경로 → Trace(Step 리스트)다. Trace 는 이미 유래를 들고 있다.

```
data      trace 길이 2
parsedURL trace 길이 5   ← data 의 트레이스로 시작한다
host      trace 길이 7   ← parsedURL 의 트레이스로 시작한다
```

`host` 가 검증됐으면 **트레이스가 `host` 의 접두사인 경로**가 곧 조상이다. 형제
(`other := data + "x"`)는 갈라진 지점이 달라 접두사가 되지 않는다. provenance 를
따로 저장하는 설계로 갔으면 훨씬 큰 변경이 됐을 것이다.

함정 하나: 조회표 형태의 검증 경로는 `parsedURL.Hostname` 인데 이건 **env 키가 아니다**
(오염을 들고 있는 건 `parsedURL`). env 에 없으면 마지막 구간을 떼며 거슬러 올라간다.

## 4. 경계선을 테스트에 박았다

무엇을 '검사'로 인정하느냐가 이 작업의 전부다. 넓히면 오탐이 줄고 재현율이 깎인다.

- 인정: 리터럴과의 `==`/`!=` (단 `nil`·`null` 비교는 제외 — 값이 있느냐를 물었을 뿐이다)
- 인정: 경로에 대한 **무인자** 메서드 호출 (`ip.IsPrivate()`)
- 불인정: `len(data) > 100` — 값을 인자로 넘겨 **다른 것**을 계산했다
- 불인정: 무관한 값 검사 · 거부하지 않는 분기 · 검사 뒤 재오염

`tests/test_derived_guard.py` 8건 중 5건이 이 '취약' 쪽이다. **여기가 깨지면 재현율을
팔아 정밀도를 산 것**이라 회귀 방지선으로 남겼다.

## 5. 곁에서 나온 것 — `url.Parse` 는 싱크가 아니다

`go_ssrf.yml` 의 sinks 에 `url.Parse` 가 들어 있었다. URL 을 파싱하는 것만으로는 아무
요청도 나가지 않는다. 이게 있으면 **URL 을 검증하는 프로그램은 전부 SSRF** 가 된다.

빼자 재현율 손실 0 으로 gin 0.152 → 0.178, net_http 0.164 → 0.188. 파생값 가드와
섞이지 않게 따로 재고 따로 기록했다.

## 7. 잃은 8건은 무엇인가

숫자만 보고 "미미하다"로 넘기지 않고 전부 열어 봤다. 여덟 건이 같은 형태다.

```js
const _host = new URL(data).hostname;
if (!_host.endsWith(".trustmesh.internal") && !_host.endsWith(".trustcdn.io")) {
  res.status(403).json({error: "forbidden host"}); return;
}
http.get(data);
```

**가드는 진짜로 존재한다.** 허용 목록이 `.trustmesh.internal` — 내부 도메인을 허용하는
것 자체가 취약점이다. 흐름 분석으로는 구분할 수 없다(`.internal` 이 내부 이름공간이라는
지식이 필요하다). 비용을 이해하고 받아들였다고 기록한다.

## 8. 측정이 판단을 대신했다

이 작업에서 배운 것은 기법이 아니라 순서다.

건전성에 논란이 있는 변경은 **켜고 끄는 스위치부터 만들고 전 범위를 잰 다음** 정한다.
미리 정하면 어느 쪽으로 정하든 근거가 없다. 켜기로 정한 뒤에는 스위치를 지웠다 —
결정이 끝난 플래그는 부채다. 근거는 이 로그와 테스트에 남는다.

# 이어서 — 미탐 278건 분해

오탐을 정리하고 나니 남은 것은 미탐이었다. gin 의 미탐 278건을 전부 열었다.

Go gin 0.322 → **0.576**, net_http 0.316 → **0.570**. 그리고 같은 수정으로
**Java 0.801 → 0.826**, **C++ 0.105 → 0.150** 이 따라 올랐다.

## 9. 내 첫 분류가 틀렸다

정규식으로 형태를 세어 표를 만들었다 — "고루틴 27건·슬라이싱 23건·구조체 리터럴 9건".
그대로 보고할 뻔했는데, 최소 재현으로 하나씩 물어보니 **고루틴·defer·슬라이싱·맵 읽기·
구조체 리터럴·즉시호출 람다는 단독으로는 전부 탐지됐다.**

정규식이 걸린다고 원인인 것이 아니다. 파일 하나에 여러 형태가 섞여 있으니 먼저 걸리는
것이 원인 자리를 차지했을 뿐이다. 어제 "적용했다와 동작한다는 다르다"를 적어 놓고
오늘은 "같이 나타난다와 원인이다"에서 같은 실수를 했다.

게다가 첫 재현 스크립트도 틀렸다. 탐지 여부를 `rule_id.startswith("go.")` 로 봤는데,
`strings.Builder` 케이스는 `WriteString` 이 XSS 싱크로 걸려 **엉뚱한 규칙이 뜬 것을
탐지로 세고 있었다.** 규칙을 특정해서 다시 재고서야 실제 모양이 보였다.

## 10. 규칙 데이터 — 싱크를 몰랐다

gin 은 `c.Data`/`c.String`/`c.HTML`, net/http 는 `w.Write` 로 응답을 쓴다. XSS 싱크
목록에는 `Fprintf` 계열만 있어 basic_xss 재현율이 **6%** 였다.

반대 방향의 실수도 있었다. bare `WriteString` 이 목록에 있어 `strings.Builder` 누적
까지 HTML 출력으로 잡고 있었다 — 미탐과 오탐을 **동시에** 만들던 한 줄이다.

`net.Dial` 이 SSRF 싱크에 없었고, `filepath.Clean` 이 **정제 목록에 있었다**. Clean 은
경로를 정규화할 뿐 선행 `../` 를 지우지 않아 경로 조작을 막지 못한다. 그것도 Go 규칙
6개에 복사돼 SQL 주입·XSS·명령 주입에서까지 정제로 쳐 주고 있었다(그쪽은 애초에 의미가
없다). 복사된 설정은 복사된 곳에서 틀린다.

여기까지가 `0.322 → 0.442`. 전부 YAML 이고 엔진은 한 줄도 안 고쳤다.

## 11. 엔진 — 오염이 끊기던 여섯 자리

| 형태 | 원인 |
|---|---|
| `b.WriteString(x); v := b.String()` | `_MUTATORS` 목록이 소문자뿐(Go·C# 은 대문자 시작) |
| `fmt.Fprintf(&sb, "%s", x)` | 결과를 첫 인자로 내주는 형태 — outcopy 미선언 |
| `for _, v := range xs` | Go 는 반복 변수가 `range_clause` 에 달려 기존 for-each 가 비껴갔다 |
| `f := func() string { return x }; f()` | 요약은 파라미터만 본다 — 인자를 받는 클로저는 멀쩡했다 |
| `go func() { ch <- x }()` | 읽는 쪽(캡처)만 고쳐져 있고 쓰는 쪽이 밖으로 안 나왔다 |
| `ch <- x` | Opaque 로 접혀 통째로 끊겼다 |

절반이 **이미 있는 장치에 이름이 빠진 것**이었다. 수신자 변경(`_MUTATORS`)은 `add`·
`put`·`write` 를 알고 있었는데 전부 소문자였다. 한 줄 목록에 열 단어를 더한 것이
`0.442 → 0.536` 이다.

경계도 같이 정했다. `for i := range xs` 는 인덱스만 받는 형태라 묶지 않는다 — 인덱스에
컬렉션의 오염을 주는 것은 과대근사가 지나치다. 채널 송신의 연산자는 `=` 가 아니다 —
채널은 컨테이너라 안전한 값을 한 번 보냈다고 앞서 담긴 오염이 사라지면 안 된다.
(`ch <- "safe"` 뒤의 `<-ch` 가 탐지되지 않는 것을 재현으로 확인했다.)

## 12. Go 를 파다 Java 가 올랐다

클로저·채널 묶음(`0.536 → 0.576`)을 전 코퍼스에 재 보니:

```
Java        0.801 → 0.826   재현율 93.4% → 95.8%, 오탐 100 그대로
C++ httplib 0.105 → 0.150   재현율 61.5% → 80.0%
C++ stand.  0.085 → 0.135   재현율 58.5% → 77.0%
JS·TS·Ruby  여섯 스위트 전부 +0.002 ~ +0.008
Python·PHP·C#·C             변화 없음
```

**가장 강한 코퍼스와 가장 약한 코퍼스가 같이 올랐다.** 어제 적은 판별 기준 그대로다 —
한 언어에서 찾은 결함이 다른 언어 점수를 올리면 코퍼스에 맞춘 것이 아니다.

## 13. 정하지 않고 남긴 것

미탐의 **29.6%(66건)는 소스를 우리가 모르는 것**이다. `DB.QueryRow(...).Scan(&v)`
57건, 파일·환경변수·stdin 9건. 코퍼스는 이걸 오염으로 친다 — 2차 주입·저장형 XSS

켜면 탐지는 늘지만 "DB 는 신뢰 경계 안"으로 보는 환경에서는 오탐이 쏟아진다. 이건
분석 기술이 아니라 **정책**이고, 제품이 고를 게 아니라 도입하는 조직이 고르는 것이다.
측정만 해 두고 정하지 않았다.

흐름 분석 밖 9건도 있다. 정규식 검증은 **패턴 내용**에 답이 갈린다 — `validInputPat`
은 안전, `^[^\x00-\x08]+$` 는 취약인데 우리 눈엔 둘 다 같은 `MatchString` 이다.

## 14. 오늘 배운 것

어제는 "건전성 논란이 있으면 스위치부터 만들고 전 범위를 재라"였고, 오늘은 그 앞 단계다.

**원인을 셀 때는 같이 나타나는 것과 원인인 것을 갈라야 한다.** 형태를 세는 정규식은
가설을 만드는 도구지 결론이 아니다. 결론은 최소 재현이 낸다 — 그리고 그 재현도 무엇을
'탐지'로 셀지 틀리면 거짓말을 한다.

## 15. 표현만 둘, 판단은 하나

C++ 오탐 130건 중 117건(90%), C 오탐 82건 전부가 같은 생각이었다.

```cpp
// 삼항
std::string safe = (data == "asc" || data == "desc") ? data : std::string("asc");

// 분기 합류
const char *safe = data;
if (strcmp(data, "/bin/echo") != 0 && strcmp(data, "/bin/cat") != 0) safe = "/bin/echo";
```

둘 다 결론이 같다 — `safe` 는 **어느 쪽을 타든 미리 정해진 값**이다. 조건이 참이면
비교한 상수 중 하나이고, 거짓이면 기본값이다. 과대근사를 푸는 게 아니라 **확정**이라
어제의 파생값 가드와 성격이 다르다. 건전성 논쟁이 필요 없었다.

## 16. 두 번 헛짚었다

**기본값을 리터럴로만 봤다.** C++ 은 `std::string("asc")` 처럼 생성자로 쓴다. 리터럴만
찾으니 130건 중 11건만 줄었다. 필요한 건 '리터럴'이 아니라 **'오염이 없는 값'** 이다 —
`_taint(반대편) is None`. 조건을 정확히 쓰는 것과 **필요한 것을 묻는 것**은 다르다.

**안쪽 if 만 봤다.** C 관용구는 준비 호출로 한 겹 더 싸여 있다.

```c
if (regcomp(&re, "^[a-z]+$", REG_EXTENDED) == 0) {
    if (regexec(&re, data, 0, NULL, 0) != 0) safe = "config";
    regfree(&re);
}
```

안쪽에서 `safe` 를 지워도 **바깥 합류에서 되살아난다** — 바깥 if 에 else 가 없으니
안 들어간 쪽 환경에는 오염이 그대로다. 82건 중 43건만 줄었다. 블록 전체를 보게 하고서야
0 이 됐다.

둘 다 "고쳤는데 덜 줄었다"로 드러났다. **부분적으로 듣는 수정은 틀린 수정**일 때가
많다 — 숫자가 절반만 움직이면 원인을 반만 잡은 것이다.

## 17. 경계선

넓히면 재현율이 깎이는 자리라 테스트로 박았다(12건 중 7건이 '취약' 쪽).

| 인정 | 불인정 |
|---|---|
| `(x == "a" \|\| x == "b") ? x : 기본값` | `(x == "a" \|\| y == "b") ? x : 기본값` — y 쪽으로 참이 될 수 있다 |
| `regex_match(x, re) ? x : 기본값` | `x.empty() ? 기본값 : x` — 값을 본 게 아니다 |
| `strcmp(x,"a") != 0` 이면 기본값 대입 | `strcmp(x,"a") == 0` 이면 대입 — 빠져나온 쪽에서 x 를 모른다 |
| | 기본값 자리에 오염이 들어가는 경우 |

`strcmp`·`regexec` 는 **리턴값 자체가 비교 결과**라 `!= 0` 이 실패를 뜻한다. 이걸
"상수와 맞춰 봤다"로 읽는 장치를 따로 뒀다.

테스트를 쓰다 또 하나 틀렸다. C 테스트가 규칙 id 를 `c.command-injection` 으로 봤는데
C 도 `cpp.` 접두 규칙을 쓴다. **아무것도 탐지되지 않으니 '안전' 항목이 공짜로 통과**
하고 있었다 — 처음엔 소스조차 안 넣어서 더 그랬다. 음성 항목을 같이 두지 않았으면
못 봤을 실수다.

## 21. 곁에서 나온 진짜 버그

정책 테스트를 쓰다 JS 쪽이 안 걸렸다. 코퍼스의 실제 형태가 이것이다.

```js
const row = (await db.query("SELECT text FROM comments")).rows[0].text;
```

`rows[0]` 에서 끊겼다. 상수 첨자 조기 종료 — `d["a"]` 가 깨끗함을 확인했으니 베이스로
되돌아가지 않는다는 최적화인데, **베이스의 경로를 모를 때도 끊고 있었다.** 베이스가
호출 결과라 경로가 안 나오면 애초에 조회가 일어나지 않았으므로 '깨끗함이 확인됐다'고
말할 수 없다.
