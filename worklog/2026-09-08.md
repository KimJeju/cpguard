## 1. 파싱 캐시가 수정을 통째로 삼켰다 (`73efc3a`)

파이썬 미탐 원인을 찾아 고쳤는데 결과가 안 바뀌었다. 같은 내용의 파일을 다른 경로로
복사해 스캔하면 탐지되고, 원본 경로에서는 미탐이었다. 파싱 캐시가 옛 IR 을 돌려주고
있었다.

캐시 키의 버전은 정규화기 소스 해시로 자동 계산하게 되어 있었다. 그런데 해시 대상이
`normalize.py`, `normalize_cfam.py`, `constfold.py` 세 개로 **손으로 나열**되어 있었고
`normalize_py.py`, `normalize_php.py` 가 빠져 있었다. 이 함수의 docstring 에 적힌
"상수를 손으로 올리는 방식은 잊기 쉽고, 잊으면 옛 IR 이 그대로 재사용돼 조용한 오류가
난다"는 실패를, 손으로 만든 목록이 그대로 재현한 셈이다.

`parse/normalize*.py` 를 glob 으로 훑게 바꿨다.

**교훈**: 자동화한 방어장치라도 그 입력이 수동 목록이면 같은 실패가 난다.

## 2. 파이썬 미탐 5종 (`bafb850`)

최소 재현으로 좁힌 결과 원인이 하나가 아니라 다섯이었다.

### 2.1 map-get 단축이 소스를 삼켰다

`request.cookies.get("x")` 는 `recv=request.cookies`, `meth=get` 로 맵 접근 단축 분기에
들어간다. `env` 가 비어 있으니 곧바로 `None` 을 돌려주고, 소스 판정(`_matches_source`)을
한 번도 거치지 못했다. Flask·Django 의 표준 관용구가 통째로 미탐이었다.

단축 자체는 `map.put("a", 오염)` 뒤 `map.get("b")` 오탐을 막는 장치라 없애지 않고,
소스로 인정되는 경로면 단축을 타지 않게 순서만 바꿨다.

### 2.2 보간 f-string 이 리터럴로 접혔다

tree-sitter 에서 `f"..{x}.."` 도 노드 타입이 `string` 이라 리터럴 집합에 걸렸다. 안에
담긴 오염이 밖으로 나오지 못했다. `interpolation` 자식이 있으면 Opaque 로 접어 합집합
전파하게 했다.

### 2.3 sink 가 호출 형태만 있었다

Flask 계열은 **핸들러의 리턴값이 그대로 응답 본문**이 된다. 호출 형태의 sink 가 아예
존재하지 않으므로 규칙에 `pattern: return` 을 더했다. 그 판정에 필요한 데코레이터를
IR 이 보존하도록 했다(전에는 버렸다).

### 2.4 누적 대입이 오염을 지웠다

`x += 안전값` 이 앞서 `x` 에 담긴 오염을 지웠다. `_run` 의 Assign 분기가 연산자를 보지
않고 무조건 `env.pop` 했기 때문이다. 언어를 가리지 않는 미탐원이라 자바 탐지도 4건 늘었다.

### 2.5 match/case 가 통째로 Opaque 로 접혔다

분기 안의 대입이 사라졌다. if 사슬로 펴서 기존 분기 합류(`_merge`)를 그대로 쓴다.

## 3. 측정 방식이 틀렸다 (`ea5f906`)

하네스가 파일을 하나씩 `scan_file` 로 돌렸다. 제품이 실제로 도는 방식(`scan_path`)과
다르고, 파일 경계를 넘는 함수 요약이 붙지 않아 공용 헬퍼가 늘 미해석으로 남는다.

`--mode project` 를 기본으로 하고 `--mode file` 을 예전 수치 비교용으로 남겼다.
흐름이 여러 파일에 걸치므로 finding 은 트레이스가 지나간 테스트 파일에 귀속시킨다.

자바 수치가 이렇게 움직였다.

```
재현율 65.1% -> 68.5%   (TP 533 -> 561)
오탐률 25.9% -> 43.3%   (FP 195 -> 326)
점수    0.392 -> 0.252
```

**점수가 내려간 것은 회귀가 아니다.** 파일 단위로 재면 `helpers/Thing1.doSomething`
같은 통과 헬퍼가 미해석으로 끊겨 취약·안전 양쪽 흐름이 다 사라진다. 프로젝트 단위로는
양쪽을 다 따라간다. 즉 **기존 0.392 는 분석을 덜 해서 나온 수치**다. 이후로는 프로젝트
단위 수치만 쓰고, 옛 수치와 직접 비교하지 않는다.

## 4. 호출 대상을 못 찾는 두 형태 (`53ab4a3`, `dff4e9e`)

### 4.1 모듈 경로로 부른 함수

호출지점에서 정의를 찾을 때 이름 정확 일치만 봤고, 레지스트리 키는 맨 함수 이름
하나뿐이었다. 파이썬에서 `import helpers.utils` 뒤 `helpers.utils.f(x)` 로 부르는 것은
표준 관용구인데, 이 형태는 정의를 영영 못 만나 흐름 전체에 불확실 표시가 찍혔다.

함수를 맨 이름과 모듈 경로를 붙인 이름 모두로 등록한다(같은 `FuncInfo` 를 공유). 스캔
루트를 모르므로 정의 파일 경로의 뒤에서부터 세 단계까지 후보를 만든다. 호출 경로의
접두가 정의 파일 위치와 맞아야 걸리므로 `db.query` 가 아무 파일의 `query` 로 잘못
해석되는 일은 없다.

판정은 완전히 동일하고 불확실 표시만 66.3% → 44.2% 로 내려갔다. **요약이 붙어도 결과가
같은 것은 설계대로다** — `propagate` 는 과대근사와 판정이 같고, 달라지는 것은 검토
비용뿐이다.

### 4.2 그 자리에서 만든 객체의 메서드

`new Test().doSomething(param)` 처럼 수신자가 식인 호출은 정의를 찾지 못해 과대근사로
통과시켰다. 자바에서 **정제 코드를 같은 파일의 내부 클래스에 두는 형태**가 흔해, 정제가
분명히 있는데도 그 코드에 도달하지 못하고 오탐이 났다. 규칙의 정제 목록에 `htmlEscape`
가 이미 들어 있었는데도 잡히지 않던 것이 이 이유다.

수신자가 식(`ir.Call`)인 호출에 한해, 같은 파일 안에서 메서드 이름으로 정의를 찾는다.
이때는 타입이 코드에 그대로 적혀 있어 안전하다.

**범위를 넓게 잡으면 안 된다는 것을 실측으로 확인했다.** 처음에는 점 경로가 나오는
호출까지 같은 파일의 동명 메서드로 이었더니, helpers 의 `ThingInterface.doSomething`
호출이 그 파일 내부 클래스의 `doSomething`(마침 분석 중인 자기 자신)으로 연결돼 오염이
통째로 사라졌다 — 취약 13건이 미탐이 됐다. 수신자가 변수인 호출에는 쓰지 않는다.

소형 코퍼스 A/B (자바 xss):

```
안전한 변형 209건 중 오탐  45 -> 8
취약한 변형 246건 중 정탐 172 -> 168
```

전체로는 재현율 68.5% → 65.9%, 오탐률 43.3% → 27.4%, 점수 0.252 → **0.386**,
불확실 25.6% → **3.6%**.

정탐 21건이 줄었다. 그동안 "정의를 못 찾아 통과시킨" 흐름이 우연히 맞았던 것들이고,
이제는 요약이 말하는 대로만 보고한다. 불확실 급감은 같은 사실의 다른 면이다.

## 5. 파이썬 라이브러리 요약 (`4d3cd7a`)

코퍼스를 돌려 불확실 표시를 만든 호출을 실제로 뽑아 채웠다. `urllib.parse` 의 인코딩·
디코딩, `base64` 왕복, `yaml` 파싱, Flask 의 `redirect`·`make_response`, bytes/str 변환과
`str.format`.

넣지 않은 것도 파일에 적어 뒀다.

| 뺀 것 | 이유 |
|---|---|
| `eval` | 리턴이 인자의 내용을 담는다고 확정할 수 없다. 그리고 `eval(사용자입력)` 은 진단원이 어차피 봐야 하는 자리다 |
| `subprocess.run` | 리턴은 `CompletedProcess` 객체다 |
| `html.escape` | 정제다. 규칙 YAML 의 `sanitizers` 담당 |
| `thing.doSomething` | 라이브러리가 아니라 코퍼스의 헬퍼다 |

판정 완전 동일, 불확실 44.2% → **13.4%**.

## 6. 컨테이너 경유 전파 (`7c6291c`)

### 6.1 슬롯을 특정할 수 없는 대입이 컨테이너 전체를 지웠다

```python
m["b"] = param          # 오염
m["c"] = "another"      # 이 한 줄로 위의 오염이 사라진다
bar = m["b"]            # 미탐
```

`path_of` 는 `m["c"]` 를 인덱스를 특정할 수 없어 베이스 `m` 으로 뭉갠다. 그 자리에
안전한 값이 들어오면 `env` 에서 `m` 을 통째로 지웠다. 대상이 그 경로 하나만 가리킬
때만 지우도록 고쳤다.

**이날 같은 계열의 버그가 세 번 나왔다** — `+=`(2.4), 첨자 대입(6.1), 그리고 아래 6.2.
"안전한 값 쓰기가 기존 오염을 지운다"는 뿌리가 같다. 다른 변종이 더 있을 수 있다.

### 6.2 `set` 이 수신자를 바꾸는 메서드 목록에 없었다

`ConfigParser.set(섹션, 키, 값)` · `List.set(i, x)` · `AtomicReference.set(x)` 모두
인자의 오염이 수신자로 옮겨간다.

### 6.3 `os.path.exists` 를 sink 로

읽기·쓰기가 아니라 존재 여부 오라클이지만, 사용자 경로를 그대로 넘기면 파일 존재를
확인해 주는 정보노출이라 CWE-22 범위에 든다. **점 경로 전체로만 적는다** — 맨 이름
`exists` 로 적으면 파일과 무관한 `exists` 까지 걸린다. 그래서 `pathlib` 의
`Path(...).exists()` 형태는 잡히지 않는다(의도한 선택).

파이썬 재현율 35.1% → **48.5%**, 카테고리별로 모두 올랐다(cmdi 53.8→69.2,
sqli 20→60, xss 41.9→61.3, codeinj 55→60, pathtraver 23.1→33.8). 자바는
540/279/206/547 로 완전히 동일, 회귀 없음.

## 틀린 가설 기록

측정 전에 세웠다가 실측에서 뒤집힌 것들이다. 같은 함정을 다시 밟지 않으려고 남긴다.

1. **"불확실 78.4% 는 하네스가 파일 단위라서다"** — 절반만 맞았다. 프로젝트 단위로
   바꿔도 66.3% 였고, 나머지는 모듈 경로 호출 미해석이라는 별개 원인이었다.
2. **"자바 오탐 급증은 `doSomething` 이름 충돌 때문이다"** — 틀렸다. `doSomething` 은
   helpers 의 항등 함수였고 제대로 해석된 것이었다. 진짜 원인은 정제가 든 내부 클래스
   메서드에 도달하지 못한 것.
3. **"별칭 등록이 자바 벤치를 3분에서 14분으로 만들었다"** — 근거가 없었다. "3분"은
   알림 도착 시각으로 추정한 값이지 측정한 값이 아니다. 요약 계산을 함수 단위로 바꿔도
   13분 55초로 같았다. **회귀 여부는 미확정**이다.

## 남은 것

1. **파이썬 pathtraver 33.8%** — 미탐 43건. `pathlib` 계열이 큰 덩어리인데 `Path.exists`
   를 sink 로 볼지 판단이 필요하다.
2. **파이썬 sqli·codeinj 오탐** — 정밀도 33%·41%. 파이썬 오탐률 30.7% 가 이 둘에 몰려 있다.
3. **자바 벤치 14분** — 프로젝트 모드 요약 계산이 직렬이다. 회귀인지 원래 그런지는
   별칭 등록만 끄고 한 번 재면 알 수 있다.

## 하지 않기로 한 것

- **컨테이너 인덱스 정밀도** (`add/add/add/remove(0)/get(1)`) — OWASP 가 일부러 판 함정이다.
  실제 코드에 없는 형태이고, 점수만 올린다.
- **`escape_for_html` 을 정제 목록에 추가** — 벤치마크 헬퍼 이름을 규칙에 넣는 것은
  점수를 올릴 뿐 도구를 낫게 하지 않는다. 오탐으로 그대로 둔다.
